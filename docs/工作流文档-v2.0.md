## 一、背景与目标

### 1.1 为什么要多 Agent

LiteShop 有 5 个相对独立的代码领地（后端、H5、官网、后台、共享层），如果用单个 LLM 会话串行开发，会话越来越长，上下文被塞满后 Agent 会"降智"——遗忘早期约束、重复犯错、输出质量下降。

多 Agent 的本质是：**把大任务拆成领地清晰、契约明确的小任务，每个任务由独立的子 Agent 执行，主 Agent 负责调度、监视、验收、决策。**

### 1.2 v2.0 与 v1.0 的关键差异

| 维度 | v1.0（CLI 版） | v2.0（IDE 版） |
|---|---|---|
| 主调度者 | 人类（你）手动巡视 4 个终端 | LLM 主 Agent（IDE 内主会话）自动调度 |
| 子 Agent | codex CLI 进程，多个终端窗口 | Task 工具启动的 subagent，一条消息可并发 |
| 领地隔离 | git worktree + 物理目录 | prompt 约束 + 主 Agent 验收 git diff |
| 会话管理 | codex resume / fork | IDE 主会话持久 + 每子 Agent 一次性 stateless |
| 计划拆解 | 人类预先准备 Prompt | 主 Agent 读 PRD v1.3 现场拆，写到 plans/ |
| 验收 | 人类手动跑验证命令 | 主 Agent 5 步自动验收，通过则启动下一个 |
| 交接文档 | handover md 文件 | 主 Agent 把上个子 Agent 的 final summary 塞进下个 Task query |

### 1.3 目标

- 主 Agent 不写业务代码，只做：拆计划、调度、验收、决策、交接
- 子 Agent 串行执行，一个完成并验收通过后才启动下一个
- 每个 subagent 领地清晰、契约明确、验证闭环
- 人类只在架构变更、合并 main、push 远程时介入

### 1.4 三条铁律（违反任何一条都会返工）

1. **契约先行**：并行开始前，API 接口、共享类型、组件 Schema 必须定死成文件，子 Agent 只消费契约，不发明契约
2. **领地隔离**：每个子 Agent 只能改自己目录下的文件；共享层变更必须经主 Agent 决策
3. **验证闭环**：每个子 Agent 完成后必须真实运行验证命令并输出结果；主 Agent 自己再跑一遍确认

## 二、IDE 环境准备

### 2.1 工具能力清单

主 Agent（IDE 内主会话）实际拥有的工具：

| 工具 | 能力 | 用途 |
|---|---|---|
| **Task** | 启动子 Agent，指定 subagent_type | 调度子 Agent 执行计划 |
| **Read/Write/Edit** | 直接读写项目文件 | 写 plans/、读 AGENTS.md、改代码 |
| **RunCommand** | 跑 PowerShell 命令 | 跑验证命令、git 操作、安装依赖 |
| **Grep/Glob/SearchCodebase** | 搜索代码 | 验收时查幻觉 import、查改动范围 |
| **TodoWrite** | 任务清单 | 跟踪当前调度进度 |
| **AskUserQuestion** | 向用户提问 | 架构变更等红线时请示用户 |
| **GetDiagnostics** | 拿语言服务报错 | tsc/mypy 报错检查 |
| **OpenPreview** | 启动本地服务器预览 | H5/官网端启动验证 |

### 2.2 subagent_type 选择

| subagent_type | 适用场景 |
|---|---|
| `general_purpose_task` | 写代码、跑测试、改文件（绝大多数子 Agent 用这个） |
| `search` | 只读代码搜索、调研架构、找依赖（不写代码） |

### 2.3 项目准备

1. **AGENTS.md**：项目根目录写 AGENTS.md（PRD v1.3 附录 E1 代码约束），子 Agent 启动时主 Agent 让它读
2. **PRD v1.3**：放在 docs/ 下，主 Agent 拆计划时读
3. **.gitignore**：`.env`、`node_modules`、`__pycache__`、`.next`、`dist`、`*.log`
4. **环境变量**：所有密钥只放 `.env`，绝不写进代码或 AGENTS.md
5. **运行时版本**：`.nvmrc` 锁 Node 22，`runtime.txt` 锁 Python 3.12

### 2.4 权限模式

IDE 用户权限模式建议设为"自动批准安全操作"：
- 文件读写、grep/glob：自动批准
- RunCommand：**需要批准**（防止子 Agent 跑 `rm -rf` / `git push --force`）
- Task 启动子 Agent：自动批准

主 Agent 在启动子 Agent 前应说明"该子 Agent 可能执行的命令类型"，让用户提前批准。

## 三、主 Agent 调度机制（核心）

### 3.1 主 Agent 职责边界

| 职责 | 是否做 | 说明 |
|---|---|---|
| 拆计划 | ✅ 是 | 读 PRD v1.3，现场写 plans/plan-{i}.md |
| 启动子 Agent | ✅ 是 | 用 Task 工具，subagent_type=general_purpose_task |
| 监视子 Agent | ✅ 是 | Task 工具同步等待返回，无需轮询 |
| 验收子 Agent | ✅ 是 | 5 步验收（见 3.4） |
| 决定通过/打回 | ✅ 是 | 通过 → 启动下一个；不通过 → 用修复模板重启 |
| 交接信息流 | ✅ 是 | 把上个子 Agent 的 final summary 塞进下个 Task query |
| 写业务代码 | ❌ 否 | 子 Agent 才写代码 |
| 架构变更决策 | ❌ 否 | 用 AskUserQuestion 请示用户 |
| git push / 合并 main | ❌ 否 | 用 AskUserQuestion 请示用户 |
| 新依赖引入 | ❌ 否 | 用 AskUserQuestion 请示用户 |

### 3.2 主 Agent 工作循环

```
主 Agent 启动
  ↓
1. 读 PRD v1.3 + AGENTS.md
  ↓
2. 现场拆计划：写 plans/INDEX.md + plans/plan-01.md ... plan-NN.md
  ↓
3. 向用户展示计划清单，请用户确认范围
  ↓
4. for i = 1 to N:
     a. 准备子 Agent prompt（含上份交接信息）
     b. Task 工具启动子 Agent i
     c. 等待子 Agent 返回 final summary
     d. 5 步验收（见 3.4）
     e. 通过 → 解析 summary 提取交接信息 → i++
     f. 不通过 → 用修复模板重启子 Agent i（最多重试 2 次）
  ↓
5. 全部完成后：向用户汇报总进度，请求合并 main
```

### 3.3 计划拆解规约

主 Agent 现场拆计划时遵循：

| 规约 | 说明 |
|---|---|
| 细粒度 | 每个计划可在 1 个子 Agent 会话内完成（约 1-3 小时） |
| 单一领地 | 一个计划只动一个目录（backend/ 或 packages/h5-app/ 等） |
| 依赖明确 | plans/plan-{i}.md 标注 `dependsOn: [plan-XX]` |
| 验收可机器化 | 必须有明确验证命令和成功标志（构建通过/测试通过/类型检查通过） |
| 契约驱动 | 按附录 D/E 决策执行，不发明契约 |
| 范围对照 PRD v1.3 | 1a 期 10 周 / 1b 期 5 周，对应 D8.1/D8.2 |

### 3.4 主 Agent 5 步验收（决定权实现）

每个子 Agent 返回 final summary 后，主 Agent 必须执行：

```python
# 主 Agent 5 步验收伪代码

def verify_subagent(plan_id, subagent_summary):
    # 步骤 1：查改动范围（防越界）
    diff = run_command("git status --porcelain")
    diff_files = run_command("git diff --name-only HEAD~1")
    territory = read_plan(plan_id).territory  # e.g. 'backend/'
    if not all(f.startswith(territory) for f in diff_files):
        return reject(f"越界改动：{diff_files}")

    # 步骤 2：跑验证命令（防假通过）
    verify_cmd = read_plan(plan_id).verify_command  # e.g. 'cd backend && pytest'
    output = run_command(verify_cmd)
    if not output.contains("passed") or output.contains("failed"):
        return reject(f"验证命令失败：{output}")

    # 步骤 3：查幻觉依赖（防 import 不存在的库）
    imports = grep(r"^import |^from ", target=territory)
    declared_deps = read_package_json().dependencies + read_requirements()
    for imp in imports:
        if imp not in declared_deps and imp not in STDLIB:
            return reject(f"幻觉依赖：{imp}")

    # 步骤 4：抽查 1-2 个文件（防空壳）
    changed_files = diff_files[:2]
    for f in changed_files:
        content = read_file(f)
        if "TODO" in content or "not implemented" in content.lower():
            return reject(f"空壳实现：{f}")

    # 步骤 5：类型检查/构建
    if territory.startswith('backend'):
        diagnostics = get_diagnostics()
        if diagnostics.has_errors():
            return reject(f"mypy 报错：{diagnostics}")
    else:
        run_command("pnpm typecheck")
        if not success:
            return reject("tsc 报错")

    return accept(subagent_summary)  # 提取交接信息，启动下一个
```

### 3.5 交接信息流

主 Agent 不写 handover 文件，直接在 Task query 里传交接信息：

```
你是 LiteShop 子 Agent，执行 plan-{i}。

【启动顺序】
1. 读 AGENTS.md（项目宪法）
2. 读 plans/plan-{i}.md（本批任务）
3. 上一个子 Agent 交接（主 Agent 直接提供）：
   - 已完成：[主 Agent 填入]
   - 关键决策：[主 Agent 填入]
   - 给下一个的提示：[主 Agent 填入]
   - 阻塞项：[主 Agent 填入]

【硬约束】
- 只改 {领地} 目录，跨领地需求在 final summary 阻塞项里说明
- 严格遵循 docs/api-contracts/
- 不引入未声明的新依赖
- 用最简实现，不提前设计二期功能
- 完成后跑验证命令，把真实输出粘进 final summary

【final summary 必须包含】（不写文件，直接在返回消息里）
1. 已完成：逐条对应 plan 任务清单
2. 验证结果：命令 + 通过/失败 + 关键数字
3. 修改文件清单：git diff --name-only 的输出
4. 阻塞项：需要主 Agent/用户决策的
5. 关键决策：为什么这么设计
6. 给下一个子 Agent 的提示：必须先看的事项、已知坑
7. worktree 状态：分支、是否已 commit、是否已 push（一律不自行 push）
```

### 3.6 串行调度的实现

主 Agent 在同一条消息里**只发一个 Task 调用**，等它返回再发下一个：

```
主 Agent：
  "启动子 Agent 1 执行 plan-01"
  → Task(subagent_type="general_purpose_task", query=子Agent1的prompt)
  ← 子 Agent 1 返回 final summary
  → 主 Agent 5 步验收
  → 通过 → "启动子 Agent 2 执行 plan-02，含交接信息"
  → Task(subagent_type="general_purpose_task", query=子Agent2的prompt+交接)
  ← 子 Agent 2 返回
  → 验收 → 启动子 Agent 3
  ...
```

**禁止**：一条消息里发多个 Task 调用并行跑（除非用户明确要求并行，且接受上下文压力）。

## 四、阶段 0：契约先行（主 Agent 自己做）

### 4.1 为什么必须先做

契约没定就启动子 Agent，各子 Agent 会各自"发明"接口：后端返回 `snake_case`，前端期望 `camelCase`；分页一个用 `page/size` 一个用 `offset/limit`。集成时这些问题集中爆发，返工量远大于写契约的时间。

### 4.2 主 Agent 操作

主 Agent 自己（不开子 Agent）按 PRD v1.3 附录 D2/E7 产出契约：

1. 读 PRD v1.3 附录 D2（接口契约）和 E7（端点清单）
2. 写 `docs/api-contracts/v1/*.yaml`（OpenAPI 3.0）
3. 写 `packages/shared-types/src/`（TS 类型 + 枚举，对应 D2.4）
4. 写 `docs/error-codes.md`（D2.2 错误码表）
5. 写 `docs/verify-commands.md`（各端验证命令）
6. 用 AskUserQuestion 请用户 review 契约

### 4.3 完成标准

- [ ] OpenAPI 文件通过 spectral lint（主 Agent 跑 `npx @stoplight/spectral-cli lint`）
- [ ] shared-types 能 `pnpm build`
- [ ] docker-compose 能起 PostgreSQL + Redis
- [ ] 用户 review 通过

## 五、阶段 1：共享层（子 Agent 执行）

### 5.1 为什么先于四端

四端都 import 共享层。共享层没完成就启动端 Agent，会自己造类型和组件，后期收敛极痛苦。

### 5.2 主 Agent 调度

```
主 Agent 拆 plan-01：shared-types 完整导出
主 Agent 拆 plan-02：shared-tokens（CSS 变量 + Tailwind 配置）
主 Agent 拆 plan-03：shared-components 基础原子组件（L1 层，E2.1）

启动子 Agent 1（plan-01，领地=packages/shared-types/）
  → 验收 → 启动子 Agent 2（plan-02，领地=packages/shared-tokens/）
  → 验收 → 启动子 Agent 3（plan-03，领地=packages/shared-components/）
```

### 5.3 子 Agent Prompt 模板

```
你是 shared-agent，领地：packages/shared-types/、shared-tokens/、shared-components/。
读 AGENTS.md 和 docs/api-contracts/v1/。

任务（plan-{i}）：
1. shared-types：补齐所有类型导出（按 D2.4 枚举 + E8.2 Schema 类型）
2. shared-tokens：CSS 变量（D1.6 site_themes 默认值）+ Tailwind v4 配置
3. shared-components：基础原子组件（Button/Input/Modal/Spinner），按 E2.1 L1 层

硬约束：
- 只改 packages/shared-* 目录
- 双构建兼容（E2.3 全部 "use client"，禁 import.meta.env / process.env）
- 公共组件必须有 Storybook（E2.4）
- 公共 API 必须有 TSDoc 注释（E4.3）

完成后运行：cd packages/shared-types && pnpm build && pnpm test
把真实输出粘进 final summary，按 3.5 模板输出交接信息。
```

## 六、阶段 2：四端串行开发（核心调度）

### 6.1 串行 vs 并行的取舍

v1.0 用 worktree 并行 4 端，v2.0 IDE 模式默认串行：
- **优点**：主 Agent 上下文压力小、验收更彻底、不互相阻塞、不撞合并冲突
- **代价**：总时长可能更长，但单人开发时协调成本远低于并行

若用户明确要求并行某批，主 Agent 可一条消息发多个 Task，但要警告：上下文压力大、验收复杂。

### 6.2 串行调度顺序（依赖驱动）

按 D8.1 1a 期阶段表：

```
plan-04: backend 骨架（认证/OSS/短信）
plan-05: backend 商品+库存（含三层库存 DDL E3.1）
plan-06: backend 订单+支付（状态机 D1.1 + 幂等 E16）
plan-07: h5-app 骨架（Vite+React+路由+Axios 封装）
plan-08: h5 商品浏览（分类/列表/详情/SKU）
plan-09: h5 购物车+下单+支付（防抖 E16.2）
plan-10: admin-app 骨架（Vite+antd5+RBAC E1.4）
plan-11: admin 商品管理+订单管理
plan-12: admin 库存+运费模板+系统设置
plan-13: 集成验证（端到端 E15.1）
```

### 6.3 主 Agent 调度示例（plan-04 → plan-05）

**主 Agent 第 4 轮**：

```
plan-04 子 Agent 已返回 final summary：
  - 已完成：用户认证 + OSS 上传签名 + 短信验证码
  - 验证：pytest 23 passed
  - 修改文件：backend/app/api/auth.py / oss.py / sms.py / ...
  - 关键决策：JWT HS256，access 2h / refresh 7d
  - 给下一个提示：user_id 类型是 bigint，下游表外键都引用它
  - 阻塞项：无

主 Agent 5 步验收通过
  ↓
主 Agent 准备 plan-05 子 Agent prompt：
  "你是 backend-agent，执行 plan-05。
   读 AGENTS.md 和 docs/api-contracts/v1/product.yaml。
   上个子 Agent 交接：user_id 类型 bigint，外键引用 users.id。
   任务：商品分类/SPU/SKU CRUD + 库存三层模型（E3.1 DDL + 原子 SQL）。
   只改 backend/。完成后跑 cd backend && pytest，按 3.5 输出。"

启动 plan-05 子 Agent
  → 等返回 → 5 步验收
  → 通过 → 准备 plan-06 prompt（含 plan-05 交接）
  → ...
```

### 6.4 批次边界

每完成 3-4 个 plan，主 Agent 用 AskUserQuestion 请示用户：
- 是否合并当前进度到 main
- 是否调整后续计划范围
- 是否有人工 review 需求

## 七、阶段 3：各端自我验证

### 7.1 子 Agent 验证要求

每个子 Agent 的 final summary 必须包含**真实验证输出**：

| 端 | 验证命令 |
|---|---|
| backend | `cd backend && ruff check . && mypy . && pytest -v --cov=app` |
| h5-app | `cd packages/h5-app && tsc --noEmit && pnpm test && pnpm build` |
| admin-app | `cd packages/admin-app && tsc --noEmit && pnpm test && pnpm build` |
| shared-* | `pnpm build && pnpm test` |

### 7.2 主 Agent 抽查

主 Agent 5 步验收时，除了跑子 Agent 报告的命令，还要：
- 检查有无 `.skip` / 注释断言 / 改测试迎合错误
- 抽查 1-2 个文件看是否真实实现（非 TODO 空壳）
- 查 import 是否在 package.json / requirements 中（防幻觉）

## 八、阶段 4：集成打通

### 8.1 集成由主 Agent 调度

最后一个 plan 是"集成验证"，主 Agent 启动一个专门的 verification-agent：

```
你是 verification-agent，领地：tests/e2e/（新建）。
环境：后端 8000 / H5 5173 / 后台 5174；账号 admin/admin123。
按 PRD v1.3 E15.1 验收清单，用 Playwright 编写并执行端到端测试：
  - 商品上架 → H5 可见
  - 加购 → 下单 → 沙箱支付 → 后台发货 → 确认收货
  - 库存并发不超卖（E3.1.2 原子 SQL）
  - 支付回调幂等（E16.3）
  - 订单超时取消与回调竞态（E12）
只改 tests/e2e/，禁止改业务代码。
输出：每个用例通过/失败 + 失败截图 + 责任端判定。
```

### 8.2 问题修复循环

```
verification-agent 报问题 → 主 Agent 按责任端判定
  → 用修复模板重启对应端子 Agent 修复
  → 子 Agent 自我验证 → 主 Agent 验收
  → 用 AskUserQuestion 请求合并 main
  → 重新跑 E2E 直到全绿
```

责任端判定依据是契约：直接 curl 后端，若后端响应不符合 OpenAPI 是后端问题；若后端正确而前端展示错是前端问题。

## 九、主 Agent Prompt 模板库

### 9.1 主 Agent 启动 Prompt（用户发给我）

```
你是 LiteShop 项目的主 Agent。读 docs/PRD-v1.3.md 和 AGENTS.md。

【你的职责】
1. 现场拆计划：写 plans/INDEX.md + plans/plan-{i}.md
2. 串行调度子 Agent：用 Task 工具，subagent_type=general_purpose_task
3. 5 步验收每个子 Agent（见 PRD E3.4 等价流程）
4. 通过则启动下一个，不通过则用修复模板重启
5. 把上个子 Agent final summary 的"给下一个的提示"塞进下个 Task query

【你的边界】
- 不写业务代码
- 架构变更/合并 main/push 远程/新依赖引入 → 用 AskUserQuestion 请示用户
- 串行调度，一次只启动一个子 Agent

【开始】
1. 读 PRD v1.3 附录 D8.1（1a 期阶段表）
2. 写 plans/INDEX.md（10-13 个细计划）
3. 写 plans/plan-01.md 到 plan-NN.md
4. 用 AskUserQuestion 展示计划清单请用户确认
5. 用户确认后启动 plan-01 子 Agent
```

### 9.2 子 Agent 通用 Prompt 模板

```
你是 LiteShop 子 Agent，执行 plan-{i}。

【启动顺序】
1. 读 AGENTS.md（项目宪法）
2. 读 plans/plan-{i}.md（本批任务）
3. {若 i>1} 上个子 Agent 交接：
   - 已完成：{主 Agent 填入}
   - 关键决策：{主 Agent 填入}
   - 给下一个的提示：{主 Agent 填入}
   - 阻塞项：{主 Agent 填入}

【硬约束】
1. 只改 {领地} 目录，跨领地需求在 final summary 阻塞项里说明
2. 严格按 docs/api-contracts/v1/ 和 packages/shared-types/
3. 不引入未声明的新依赖
4. 用最简实现，不提前设计二期功能
5. 写操作按钮必须用 useDebounceAction Hook（PRD E16.2）
6. 公共 API 必须有 TSDoc/docstring（PRD E4.3）
7. 金额一律整数分（PRD D1.2）
8. 禁止 git push / git push --force / rm -rf

【完成后输出 final summary】（不写文件，直接返回）
1. 已完成：逐条对应 plan 任务清单
2. 验证结果：命令 + 通过/失败 + 关键数字
3. 修改文件清单：git diff --name-only 输出
4. 阻塞项：需要主 Agent/用户决策的
5. 关键决策：为什么这么设计
6. 给下一个子 Agent 的提示
7. worktree 状态：分支、是否 commit、是否 push（不自行 push）
```

### 9.3 修复模板（不通过时用）

```
你是 {角色}。修复以下问题：
现象：{主 Agent 填入}；复现：{步骤}；报错：{日志}；预期：{预期}
只改 {领地}。先定位根因再改，不要 try/except 吞错或注释掉问题代码。
修复后跑 {相关测试}，在 final summary 说明根因、改动文件、影响范围。
```

### 9.4 只读审查模板（用 subagent_type=search）

```
只读审查 {目录/文件}，不要修改：
1. 是否违反 AGENTS.md（领地、技术栈、金额处理、动态样式）
2. 是否有安全问题（SQL 拼接、未验签、密钥硬编码、XSS）
3. 是否有并发/状态机/空值处理隐患
4. 是否有幻觉依赖（import 不存在的库）
5. 是否符合 PRD E16 防抖规约
输出按严重程度排序的问题清单，每条给文件:行号和修复建议。
```

## 十、Git 策略（IDE 适配）

### 10.1 分支模型

- `main`：始终可运行，所有计划完成后合并
- `feat/{scope}-{slug}`：每个子 Agent 在自己分支干活，但 IDE 模式下分支可简化为 `feat/plan-{i}`
- 子 Agent 完成后小步 commit，message 用 `feat(scope): xxx`

### 10.2 提交粒度

- 一个模块/一次验证通过即 commit
- 子 Agent 在 final summary 里报告 commit hash 列表
- 主 Agent 验收通过后，**不自行合并 main**，用 AskUserQuestion 请示用户

### 10.3 回滚

| 场景 | 操作 |
|---|---|
| 子 Agent 改坏单文件 | `git checkout -- 文件`（主 Agent 跑） |
| 子 Agent 改坏一片 | `git reset --hard HEAD~N`（主 Agent 跑，需用户批准） |
| 整个方向错 | 主 Agent 用 AskUserQuestion 请示是否废弃整个 plan |

### 10.4 禁止操作

子 Agent 禁止自行执行：
- `git push`（任何远程推送）
- `git push --force` / `git reset --hard`
- `rm -rf`
- `DROP TABLE`
- 部署/发版/镜像推送

这些操作主 Agent 也不做，全部用 AskUserQuestion 请示用户。

## 十一、注意事项与坑点

### 11.1 调度类

1. **一次只启动一个子 Agent**：并行会撑爆主 Agent 上下文，验收难
2. **子 Agent 是 stateless 的**：每次 Task 调用不共享上下文，交接信息必须主 Agent 显式传
3. **主 Agent 不写业务代码**：保持主 Agent 上下文干净，专注调度
4. **主 Agent 5 步验收必跑**：不能听子 Agent 说"通过了"就信
5. **批次边界请示用户**：每 3-4 个 plan 用 AskUserQuestion 同步进度

### 11.2 上下文类

6. **子 Agent 别跑超长任务**：单 plan 控制在 1-3 小时内，避免降智
7. **交接信息精简**：主 Agent 塞给下个 Task 的交接信息控制在 500 字内，只传关键决策和阻塞项
8. **plans/plan-{i}.md 是单一信息源**：子 Agent 从文件读任务，主 Agent 不在 query 里重复任务详情
9. **AGENTS.md 沉淀稳定约束**：技术栈/领地/规约写进 AGENTS.md，子 Agent 自动读，主 Agent 不重复说

### 11.3 技术协同类

10. **契约是责任端判定唯一依据**：集成时用 curl 直打后端，对照 OpenAPI 判定
11. **金额一律整数分**：D1.2 全链路规约
12. **状态机用乐观锁**：D1.1 `UPDATE ... WHERE status=:old`
13. **写操作防抖+幂等**：E16 双层防护
14. **共享组件双构建兼容**：E2.3 全部 "use client"
15. **公共 API 注释**：E4.3 TSDoc/docstring

### 11.4 代码质量类

16. **子 Agent 假通过测试**：主 Agent 必查 `.skip` / 注释断言 / 改测试迎合
17. **幻觉依赖**：子 Agent 会 import 不存在的库，主 Agent 用 Grep 查 package.json
18. **过度工程化**：子 Agent 倾向加抽象层，prompt 里要求"最简实现"
19. **吞异常**：子 Agent 喜欢空 except，主 Agent 用 Grep 查 `except.*pass`
20. **死代码不清理**：废弃文件/函数让子 Agent 顺手删

### 11.5 安全类（红线）

21. **永不连生产环境**：子 Agent 的 DB/Redis/OSS/支付全指向本地/沙箱
22. **密钥只进 .env**：子 Agent 不得把密钥写进代码/AGENTS.md/commit
23. **危险命令需用户批准**：rm -rf / git push --force / DROP TABLE 一律拒绝
24. **支付/鉴权/迁移代码人工 review**：主 Agent 完成后用 AskUserQuestion 请用户 review
25. **不让子 Agent 自行对外发布**：部署/发版/推送镜像全部用户手动

## 十二、人工介入红线

| 类型 | 具体事项 |
|---|---|
| 架构决策 | 技术栈变更、服务拆分、数据库表结构大改、缓存方案 |
| 契约变更 | API 字段增删、枚举变更、分页/错误格式调整 |

| 数据安全 | 数据库迁移（删列/回填）、生产数据操作、备份策略 |
| 对外操作 | git push、发版、部署、域名/证书、第三方商户配置 |

### 附录 B：主 Agent 单次调度循环 SOP

1. 准备子 Agent prompt（含上份交接信息）
2. 用 Task 工具启动子 Agent，subagent_type=general_purpose_task
3. 等待子 Agent 返回 final summary
4. 5 步验收：
   a. `git status` 查改动范围
   b. 跑子 Agent 报告的验证命令
   c. Grep 查幻觉 import
   d. Read 抽查 1-2 个文件
   e. GetDiagnostics 或跑 tsc/mypy
5. 通过 → 解析 final summary 提取交接信息 → 准备下个 prompt
6. 不通过 → 用修复模板重启该子 Agent（最多 2 次重试）
7. 每 3-4 个 plan 用 AskUserQuestion 同步用户

### 附录 C：出问题时的快速定位

| 现象 | 主 Agent 第一步动作 |
|---|---|
| 子 Agent 越界改文件 | `git diff --name-only` 确认越界 → `git checkout -- 文件` 还原 → 用修复模板重启 |
| 子 Agent 卡住反复报错 | 看完整报错 → 若是上下文混乱，用更细的 plan 重启 |
| 子 Agent 说完成但构建失败 | 主 Agent 自己跑命令拿真实报错 → 用修复模板打回 |
| 前后端联调对不上 | 用 RunCommand 跑 curl 直打后端，对照 OpenAPI 判定责任端 |
| 子 Agent 改坏一片 | `git reset --hard HEAD~N`（需用户批准）→ 重做该 plan |
| 主 Agent 上下文压力大 | 把已完成 plan 的交接信息精简，只保留关键决策和阻塞项 |
