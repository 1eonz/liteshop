## 一、背景与目标

### 1.1 为什么要多 Agent

LiteShop 有 5 个相对独立的代码领地（后端、H5、官网、后台、共享层），如果用单个 LLM 会话串行开发，会话越来越长，上下文被塞满后 Agent 会"降智"——遗忘早期约束、重复犯错、输出质量下降。

多 Agent 的本质是：**把大任务拆成领地清晰、契约明确的小任务，每个任务由独立的子 Agent 执行，主 Agent 负责调度、监视、验收、决策。**

### 1.2 v2.x 与 v1.0 的关键差异

| 维度 | v1.0（CLI 版） | v2.x（IDE 版） |
|---|---|---|
| 主调度者 | 人类（你）手动巡视 4 个终端 | LLM 主 Agent（IDE 内主会话）自动调度 |
| 子 Agent | codex CLI 进程，多个终端窗口 | Task 工具启动的 subagent，一条消息可并发 |
| 领地隔离 | git worktree + 物理目录 | prompt 约束 + 主 Agent 验收 git diff |
| 会话管理 | codex resume / fork | IDE 主会话持久 + 每子 Agent 一次性 stateless |
| 计划拆解 | 人类预先准备 Prompt | 主 Agent 读 PRD v1.3 现场拆，写到 plans/ |
| 验收 | 人类手动跑验证命令 | 主 Agent 5+1 步自动验收（AGENTS.md §8.2），通过则启动下一个 |
| 交接文档 | handover md 文件 | 主 Agent 把上个子 Agent 的 final summary 塞进下个 Task query |

### 1.3 目标

- 主 Agent 不写业务代码，只做：拆计划、调度、验收、决策、交接
- 子 Agent 串行执行，一个完成并验收通过后才启动下一个
- 每个 subagent 领地清晰、契约明确、验证闭环
- 人类只在架构变更、合并 main、push 远程时介入

### 1.4 三条铁律（违反任何一条都会返工）

1. **契约先行**：并行开始前，API 接口、共享类型、组件 Schema 必须定死成文件，子 Agent 只消费契约，不发明契约
2. **领地隔离**：每个子 Agent 只能改自己目录下的文件；共享层变更必须经主 Agent 决策
3. **验证闭环**：每个子 Agent 完成后必须真实运行验证命令并输出结果；主 Agent 自己再跑一遍确认

## 二、IDE 环境准备

### 2.1 工具能力清单

主 Agent（IDE 内主会话）实际拥有的工具：

| 工具 | 能力 | 用途 |
|---|---|---|
| **Task** | 启动子 Agent，指定 subagent_type | 调度子 Agent 执行计划 |
| **Read/Write/Edit** | 直接读写项目文件 | 写 plans/、读 AGENTS.md、改代码 |
| **RunCommand** | 跑 PowerShell 命令 | 跑验证命令、git 操作、安装依赖 |
| **Grep/Glob/SearchCodebase** | 搜索代码 | 验收时查幻觉 import、查改动范围 |
| **TodoWrite** | 任务清单 | 跟踪当前调度进度 |
| **AskUserQuestion** | 向用户提问 | 架构变更等红线时请示用户 |
| **GetDiagnostics** | 拿语言服务报错 | tsc/mypy 报错检查 |
| **OpenPreview** | 启动本地服务器预览 | H5/官网端启动验证 |

### 2.2 subagent_type 选择

| subagent_type | 适用场景 |
|---|---|
| `general_purpose_task` | 写代码、跑测试、改文件（绝大多数子 Agent 用这个） |
| `search` | 只读代码搜索、调研架构、找依赖（不写代码） |

### 2.3 项目准备

1. **AGENTS.md**：项目根目录写 AGENTS.md（PRD v1.3 附录 E1 代码约束 + §八调度机制），子 Agent 启动时主 Agent 让它读
2. **PRD v1.3**：放在 docs/ 下，主 Agent 拆计划时按 AGENTS.md §8.5.2 三层分层读
3. **.gitignore**：`.env`、`node_modules`、`__pycache__`、`.next`、`dist`、`*.log`
4. **环境变量**：所有密钥只放 `.env`，绝不写进代码或 AGENTS.md
5. **运行时版本**：`.nvmrc` 锁 Node 22，`runtime.txt` 锁 Python 3.12

### 2.4 权限模式

IDE 用户权限模式建议设为"自动批准安全操作"：
- 文件读写、grep/glob：自动批准
- RunCommand：**需要批准**（防止子 Agent 跑 `rm -rf` / `git push --force`）
- Task 启动子 Agent：自动批准

主 Agent 在启动子 Agent 前应说明"该子 Agent 可能执行的命令类型"，让用户提前批准。

## 三、主 Agent 调度机制（机制见 AGENTS.md §八）

### 3.1 职责边界

主 Agent 职责边界表以 **AGENTS.md §8.1** 为准（拆计划/启动/监视/验收/交接 ✅，写业务代码/架构变更/push/新依赖 ❌），本文不重复定义。

### 3.2 主 Agent 工作循环

```
主 Agent 启动
  ↓
1. 读 PRD v1.3（分层读，AGENTS.md §8.5.2）+ AGENTS.md
  ↓
2. 调用 project-radar（AGENTS.md §8.5）生成 project-context.md
  ↓
3. 现场拆计划：写 plans/INDEX.md + plans/plan-01.md ... plan-NN.md
  ↓
4. 向用户展示计划清单，请用户确认范围
  ↓
5. 按批次调度（AGENTS.md §8.3 试点校准）：
     试点批 plan-01+04 → 人工 review + go/no-go
     第二批 plan-05+06 → 人工 review 事务代码
     后续批每 3 个一批，对照基线检查
   批内每个 plan：
     a. 准备子 Agent prompt（含上份交接信息）
     b. Task 工具启动子 Agent i
     c. 等待子 Agent 返回 final summary
     d. 5+1 步验收（AGENTS.md §8.2）
     e. 通过 → 解析 summary 提取交接信息 → 下一个
     f. 不通过 → 用修复模板重启子 Agent i（最多重试 2 次）
  ↓
6. 全部完成后：向用户汇报总进度，请求合并 main
```

### 3.3 计划拆解规约

主 Agent 现场拆计划时遵循：

| 规约 | 说明 |
|---|---|
| 细粒度 | 每个计划可在 1 个子 Agent 会话内完成（约 1-3 小时） |
| 单一领地 | 一个计划只动一个目录（backend/ 或 packages/h5-app/ 等） |
| 依赖明确 | plans/plan-{i}.md 标注 `dependsOn: [plan-XX]` |
| 验收可机器化 | 必须有明确验证命令和成功标志（构建通过/测试通过/类型检查通过） |
| 契约驱动 | 按附录 D/E 决策执行，不发明契约 |
| 范围对照 PRD v1.3 | 1a 期只拆 §7.1 标注 `[1a]` 的项（提取规则 AGENTS.md §8.5.1）；plan 范围对照 AGENTS.md §8.5.2 映射表 |

### 3.4 验收（5+1 步）

完整定义（含第 6 步重复检测的 7 类检测规则）见 **AGENTS.md §8.2**，本文不重复。概要：查改动范围 → 跑验证命令 → 查幻觉依赖 → 抽查文件 → 类型检查/构建 → 重复检测（project-radar）。

### 3.5 交接信息流

交接的 4 项内容（已完成/关键决策/给下一个的提示/阻塞项，500 字内）见 **AGENTS.md §8.4**；子 Agent prompt 完整模板见 **提示词.md**（唯一事实源）。

### 3.6 串行调度与试点校准

一条消息只发一个 Task 调用。批次划分（试点批 plan-01+04 → 第二批 plan-05+06 → 后续每 3 个一批）与 go/no-go 量化阈值见 **AGENTS.md §8.3**。

### 3.7 project-radar（项目雷达）

5 步核心流程（扫描→分析→提示→覆盖检查→生成）、运行时机、project-context.md 的 6 部分结构，见 **AGENTS.md §8.5**。本文不重复。

## 四、阶段 0：契约先行（主 Agent 自己做）

### 4.1 为什么必须先做

契约没定就启动子 Agent，各子 Agent 会各自"发明"接口：后端返回 `snake_case`，前端期望 `camelCase`；分页一个用 `page/size` 一个用 `offset/limit`。集成时这些问题集中爆发，返工量远大于写契约的时间。

### 4.2 主 Agent 操作

主 Agent 自己（不开子 Agent）按 PRD v1.3 附录 D2/E7 产出契约：

1. 读 PRD v1.3 附录 D2（接口契约）和 E7（端点清单）
2. 写 `docs/api-contracts/v1/*.yaml`（OpenAPI 3.0）
3. 写 `packages/shared-types/src/`（TS 类型 + 枚举，对应 D2.4）
4. 写 `docs/error-codes.md`（D2.2 错误码表）
5. 写 `docs/verify-commands.md`（各端验证命令）
6. 用 AskUserQuestion 请用户 review 契约

**用户 review 契约时必须真读 OpenAPI，不要只点确认**。重点核对（Agent 最容易"看起来对"的地方）：
- 支付回调：验签、幂等键、金额校验、状态流转
- 库存扣减：原子 SQL 条件、锁定/回滚路径
- 订单状态机：枚举值、非法流转拒绝
- 金额：全链路 integer 分
- 分页/错误码格式统一

### 4.3 完成标准

- [ ] OpenAPI 文件通过 spectral lint（主 Agent 跑 `npx @stoplight/spectral-cli lint`）
- [ ] shared-types 能 `pnpm build`
- [ ] docker-compose 能起 PostgreSQL + Redis
- [ ] 用户 review 通过（真读，非默认确认）

## 五、阶段 1：共享层（子 Agent 执行）

### 5.1 为什么先于四端

四端都 import 共享层。共享层没完成就启动端 Agent，会自己造类型和组件，后期收敛极痛苦。

### 5.2 主 Agent 调度

```
主 Agent 拆 plan-01：shared-types 完整导出
主 Agent 拆 plan-02：shared-tokens（CSS 变量 + Tailwind 配置）
主 Agent 拆 plan-03：shared-components 基础原子组件（L1 层，E2.1）

启动子 Agent 1（plan-01，领地=packages/shared-types/）
  → 验收 → 启动子 Agent 2（plan-02，领地=packages/shared-tokens/）
  → 验收 → 启动子 Agent 3（plan-03，领地=packages/shared-components/）
```

（试点校准批次中 plan-01 先行、plan-02/03 编入后续批，见 AGENTS.md §8.3。）

### 5.3 子 Agent Prompt 模板

见 **提示词.md**（唯一事实源），主 Agent 按模板构造 Task query。

## 六、阶段 2：四端串行开发（核心调度）

### 6.1 串行 vs 并行的取舍

v1.0 用 worktree 并行 4 端，v2.x IDE 模式默认串行：
- **优点**：主 Agent 上下文压力小、验收更彻底、不互相阻塞、不撞合并冲突
- **代价**：总时长可能更长，但单人开发时协调成本远低于并行

若用户明确要求并行某批，主 Agent 可一条消息发多个 Task，但要警告：上下文压力大、验收复杂。

### 6.2 串行调度顺序（依赖驱动）

各 plan 的范围与 PRD 章节以 **AGENTS.md §8.5.2 映射表**为唯一事实源，此处仅为顺序概览：

```
plan-01~03: shared 层（types / tokens / components）
plan-04: backend 骨架（认证 / OSS / 短信）
plan-05: backend 商品 + 库存（三层库存 DDL E3.1）
plan-06: backend 订单 + 支付（状态机 D1.1 + 幂等 E16）
plan-07: h5-app 骨架（Vite + React + 路由 + Axios 封装）
plan-08: h5 商品浏览（分类 / 列表 / 详情 / SKU）
plan-09: h5 购物车 + 下单 + 支付（防抖 E16.2）
plan-10: admin-app 骨架（Vite + antd5 + RBAC D1.4）
plan-11: admin 商品管理 + 订单管理
plan-12: admin 库存（含预警 D6.4）+ 运费模板（D6.5）+ 数据看板（PRD 4.2.1）+ 系统设置 + feature_flags（E5.4）+ a11y 终检
plan-13: 集成验证（端到端 E15.1）
```

### 6.3 主 Agent 调度示例（plan-04 → plan-05）

**主 Agent 第 4 轮**：

```
plan-04 子 Agent 已返回 final summary：
  - 已完成：用户认证 + OSS 上传签名 + 短信验证码
  - 验证：pytest 23 passed
  - 修改文件：backend/app/api/auth.py / oss.py / sms.py / ...
  - 关键决策：JWT HS256，access 2h / refresh 7d
  - 给下一个提示：user_id 类型是 bigint，下游表外键都引用它
  - 阻塞项：无

主 Agent 5+1 步验收（AGENTS.md §8.2）通过
  ↓
主 Agent 准备 plan-05 子 Agent prompt：
  "你是 backend-agent，执行 plan-05。
   读 AGENTS.md 和 docs/api-contracts/v1/product.yaml。
   上个子 Agent 交接：user_id 类型 bigint，外键引用 users.id。
   任务：商品分类/SPU/SKU CRUD + 库存三层模型（E3.1 DDL + 原子 SQL）。
   只改 backend/。完成后跑 cd backend && pytest，按提示词.md 模板输出。"

启动 plan-05 子 Agent
  → 等返回 → 5+1 步验收
  → 通过 → 准备 plan-06 prompt（含 plan-05 交接）
  → ...
```

### 6.4 批次边界

每完成一批（试点批/第二批/后续每 3 个），主 Agent 用 AskUserQuestion 请示用户：
- 是否合并当前进度到 main
- 是否调整后续计划范围
- 对照试点基线的三个数（验收耗时/返工次数/可留用比例）是否劣化

## 七、阶段 3：各端自我验证

### 7.1 子 Agent 验证要求

每个子 Agent 的 final summary 必须包含**真实验证输出**：

| 端 | 验证命令 |
|---|---|
| backend | `cd backend && ruff check . && mypy . && pytest -v --cov=app` |
| h5-app | `cd packages/h5-app && tsc --noEmit && pnpm test && pnpm build` |
| admin-app | `cd packages/admin-app && tsc --noEmit && pnpm test && pnpm build` |
| shared-* | `pnpm build && pnpm test` |

### 7.2 主 Agent 抽查

主 Agent 5+1 步验收时，除了跑子 Agent 报告的命令，还要：
- 检查有无 `.skip` / 注释断言 / 改测试迎合错误
- 抽查 1-2 个文件看是否真实实现（非 TODO 空壳）
- 查 import 是否在 package.json / requirements 中（防幻觉）

## 八、阶段 4：集成打通

### 8.1 集成由主 Agent 调度

最后一个 plan 是"集成验证"，主 Agent 启动一个专门的 verification-agent：

```
你是 verification-agent，领地：tests/e2e/（新建）。
环境：后端 8000 / H5 5173 / 后台 5174；账号 admin/admin123。
按 PRD v1.3 E15.1 验收清单，用 Playwright 编写并执行端到端测试：
  - 商品上架 → H5 可见
  - 加购 → 下单 → 沙箱支付 → 后台发货 → 确认收货
  - 库存并发不超卖（E3.1.2 原子 SQL）
  - 支付回调幂等（E16.3）
  - 订单超时取消与回调竞态（E12）
只改 tests/e2e/，禁止改业务代码。
输出：每个用例通过/失败 + 失败截图 + 责任端判定。
```

### 8.2 问题修复循环

```
verification-agent 报问题 → 主 Agent 按责任端判定
  → 用修复模板重启对应端子 Agent 修复
  → 子 Agent 自我验证 → 主 Agent 验收
  → 用 AskUserQuestion 请求合并 main
  → 重新跑 E2E 直到全绿
```

责任端判定依据是契约：直接 curl 后端，若后端响应不符合 OpenAPI 是后端问题；若后端正确而前端展示错是前端问题。

## 十、Git 策略（IDE 适配）

### 10.1 分支模型

- `main`：始终可运行，所有计划完成后合并
- `feat/{scope}-{slug}`：每个子 Agent 在自己分支干活，但 IDE 模式下分支可简化为 `feat/plan-{i}`
- 子 Agent 完成后小步 commit，message 用 `feat(scope): xxx`

### 10.2 提交粒度

- 一个模块/一次验证通过即 commit
- 子 Agent 在 final summary 里报告 commit hash 列表
- 主 Agent 验收通过后，**不自行合并 main**，用 AskUserQuestion 请示用户

### 10.3 回滚

| 场景 | 操作 |
|---|---|
| 子 Agent 改坏单文件 | `git checkout -- 文件`（主 Agent 跑） |
| 子 Agent 改坏一片 | `git reset --hard HEAD~N`（主 Agent 跑，需用户批准） |
| 整个方向错 | 主 Agent 用 AskUserQuestion 请示是否废弃整个 plan |

### 10.4 禁止操作

子 Agent 禁止自行执行：
- `git push`（任何远程推送）
- `git push --force` / `git reset --hard`
- `rm -rf`
- `DROP TABLE`
- 部署/发版/镜像推送

这些操作主 Agent 也不做，全部用 AskUserQuestion 请示用户。

## 十一、注意事项与坑点

### 11.1 调度类

1. **一次只启动一个子 Agent**：并行会撑爆主 Agent 上下文，验收难
2. **子 Agent 是 stateless 的**：每次 Task 调用不共享上下文，交接信息必须主 Agent 显式传
3. **主 Agent 不写业务代码**：保持主 Agent 上下文干净，专注调度
4. **主 Agent 5+1 步验收必跑**：不能听子 Agent 说"通过了"就信（完整步骤 AGENTS.md §8.2）
5. **批次边界请示用户**：每批结束用 AskUserQuestion 同步进度 + 对照试点基线

### 11.2 上下文类

6. **子 Agent 别跑超长任务**：单 plan 控制在 1-3 小时内，避免降智
7. **交接信息精简**：主 Agent 塞给下个 Task 的交接信息控制在 500 字内，只传关键决策和阻塞项
8. **plans/plan-{i}.md 是单一信息源**：子 Agent 从文件读任务，主 Agent 不在 query 里重复任务详情
9. **AGENTS.md 沉淀稳定约束**：技术栈/领地/规约写进 AGENTS.md，子 Agent 自动读，主 Agent 不重复说

### 11.3 技术协同类

10. **契约是责任端判定唯一依据**：集成时用 curl 直打后端，对照 OpenAPI 判定
11. **金额一律整数分**：D1.2 全链路规约
12. **状态机用乐观锁**：D1.1 `UPDATE ... WHERE status=:old`
13. **写操作防抖+幂等**：E16 双层防护
14. **共享组件双构建兼容**：E2.3 全部 "use client"
15. **公共 API 注释**：E4.3 TSDoc/docstring

### 11.4 代码质量类

16. **子 Agent 假通过测试**：主 Agent 必查 `.skip` / 注释断言 / 改测试迎合
17. **幻觉依赖**：子 Agent 会 import 不存在的库，主 Agent 用 Grep 查 package.json
18. **过度工程化**：子 Agent 倾向加抽象层，prompt 里要求"最简实现"
19. **吞异常**：子 Agent 喜欢空 except，主 Agent 用 Grep 查 `except.*pass`
20. **死代码不清理**：废弃文件/函数让子 Agent 顺手删

### 11.5 安全红线

见 **AGENTS.md §六 安全红线**（永不连生产/密钥只进 .env/危险命令需批准/支付鉴权迁移人工 review 等），本文不重复。

### 附录 B：主 Agent 单次调度循环 SOP

1. 准备子 Agent prompt（含上份交接信息）
2. 用 Task 工具启动子 Agent，subagent_type=general_purpose_task
3. 等待子 Agent 返回 final summary
4. **5+1 步验收（完整定义见 AGENTS.md §8.2）**：
   a. `git status` 查改动范围
   b. 跑子 Agent 报告的验证命令
   c. Grep 查幻觉 import
   d. Read 抽查 1-2 个文件
   e. GetDiagnostics 或跑 tsc/mypy
   f. 重复检测（project-radar 对照 project-context.md）
5. 通过 → 解析 final summary 提取交接信息 → 准备下个 prompt
6. 不通过 → 用修复模板重启该子 Agent（最多 2 次重试）
7. 每批结束（试点批/第二批/后续每 3 个）用 AskUserQuestion 同步用户 + 对照基线三个数

### 附录 C：出问题时的快速定位

| 现象 | 主 Agent 第一步动作 |
|---|---|
| 子 Agent 越界改文件 | `git diff --name-only` 确认越界 → `git checkout -- 文件` 还原 → 用修复模板重启 |
| 子 Agent 卡住反复报错 | 看完整报错 → 若是上下文混乱，用更细的 plan 重启 |
| 子 Agent 说完成但构建失败 | 主 Agent 自己跑命令拿真实报错 → 用修复模板打回 |
| 前后端联调对不上 | 用 RunCommand 跑 curl 直打后端，对照 OpenAPI 判定责任端 |
| 子 Agent 改坏一片 | `git reset --hard HEAD~N`（需用户批准）→ 重做该 plan |
| 主 Agent 上下文压力大 | 把已完成 plan 的交接信息精简，只保留关键决策和阻塞项 |
| 试点批三个数不达标 | no-go：修 Skills 配置/提示词/plan 粒度后重跑，不带病放行 |
