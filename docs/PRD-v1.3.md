## 一、产品概述

### 1.1 产品定位

LiteShop 是一款面向中小商家（单店/品牌方/个体工商户）的轻量级独立商城与官网一体化系统，核心特点：

- **低代码装修**：商家通过可视化拖拽搭建 H5 商城页面和官网页面，无需写代码
- **ERP 化后台**：后台不只是商品上下架，而是覆盖商品、订单、库存、采购、财务、售后的轻量进销存
- **官网即开即用**：内置官网低代码搭建，支持多页面路由、导航菜单、SEO 配置、滚动动画、3D 效果
- **轻量部署**：单服务器 Docker Compose 一键部署，中小商家可私有化使用，也可 SaaS 化

### 1.2 目标用户

| 用户类型 | 特征 | 核心诉求 |
|---|---|---|
| 中小商家/个体工商户 | 单店经营，SKU 50-2000，日订单 < 500 | 低成本开店、自己能装修页面、管清楚库存和订单 |
| 品牌方/区域经销商 | 有自有品牌，需要独立商城沉淀私域 + 官网展示品牌 | 品牌化官网、商城交易、会员管理、多渠道库存 |
| 技术服务商/代运营 | 帮多个客户搭建商城和官网 | 可复用、低代码快速交付、多租户（二期） |

### 1.3 核心价值主张

> 让中小商家用一台服务器、一个下午，拥有一个自己能装修、能管进销存、能展示品牌的独立商城与官网。

### 1.4 产品愿景与版本规划

- **一期**：跑通商城"装修 → 上架 → 下单 → 支付 → 发货 → 进销存"完整闭环 + 商城低代码搭建
- **二期**：官网低代码搭建（多页面路由 + 18 个官网组件 + GSAP 滚动动画 + SEO）
- **三期**：3D 动画实验、多租户 SaaS 化、营销工具（优惠券/拼团/分销）、多端（小程序/APP）、AI 商品文案生成、智能补货建议

## 二、需求背景与目标

### 2.1 问题背景

1. 现有 SaaS 商城（有赞/微盟）年费高（数千至数万），且数据不在自己手里
2. 开源商城（CRMEB/萤火）功能臃肿，二次开发成本高，后台不是 ERP 思路
3. 中小商家不会写代码，但希望自己能改页面、调样式
4. 商家最痛的不是"能不能下单"，而是"库存准不准、订单乱不乱、钱对不对得上"
5. 品牌方需要独立官网展示品牌形象，但官网和商城往往是两套系统，数据不通、维护成本高
6. 现有官网搭建工具（凡科/建站之星）模板僵化，无法和商城数据打通，且动画/3D 效果差

### 2.2 业务目标

| 指标 | 一期目标 | 二期目标（官网） |
|---|---|---|
| 核心交易闭环 | 商品→购物车→下单→支付→发货→确认收货，全流程可用 | — |
| 低代码搭建 | 支持 10 个商城基础组件，商家可独立搭建首页 | 支持 18 个官网组件，多页面路由，商家可独立搭建整站 |
| 部署成本 | 单台 4C8G 云服务器可承载日订单 500 | 官网 SSG + CDN，首屏 LCP < 2s |
| 首屏加载 | H5 首页首屏 < 2s（4G 网络） | 官网首页 LCP < 2.0s，CLS < 0.1 |
| 库存准确率 | 订单扣减/取消回滚零超卖 | — |
| SEO | — | 官网页面自动生成 sitemap、结构化数据、Meta 标签 |

### 2.3 成功指标

- 商家从部署到上架第一个商品 < 30 分钟
- 商家独立完成商城首页装修 < 1 小时（无需技术支持）
- 商家独立完成官网整站搭建 < 半天（首页 + 关于 + 产品 + 联系）
- 订单状态流转零人工干预错误
- 支付回调处理零重复发货
- 官网 Core Web Vitals 全部达标（LCP < 2s, INP < 200ms, CLS < 0.1）

### 3.2 端划分

| 端 | 技术选型 | 渲染方式 | 为什么 |
|---|---|---|---|
| **商城 H5 端** | Vite + React 18 + React Router | CSR（客户端渲染） | 商城是登录后应用，SEO 需求弱，CSR 足够 |
| **官网端** | Next.js 14+ App Router | SSG/ISR（静态生成/增量再生） | 官网核心需求是 SEO 和首屏性能，SSG 是 2026 年标准方案；React 语法和商城端一致 |
| **管理后台** | Vite + React 18 + antd 5 | CSR | 后台是内部工具，CSR 即可 |
| **共享层** | shared-components / shared-tokens / shared-types | — | 商城低代码组件和官网低代码组件共享同一套 SchemaRenderer 渲染引擎和 Design Tokens |

**为什么官网端单独用 Next.js 而不是全部迁移**：商城 H5 不需要 SEO，Next.js 的 App Router 对商城这种强交互应用反而增加复杂度；官网是内容展示型，SSG 性能极好。两者共享 React 组件库，构建工具不同但组件本身是构建无关的。

### 3.4 低代码渲染引擎（共享）

所有低代码页面（商城页 + 官网页）共享同一套 Schema 格式和渲染引擎：

```typescript
// 页面 Schema 统一格式
interface PageSchema {
  pageStyle: PageStyle;           // 页面级样式（背景/内边距）
  seo?: PageSEO;                  // SEO 配置（仅官网页）
  animation?: PageAnimation;      // 页面级动画配置（仅官网页）
  components: ComponentSchema[];  // 组件列表
}

interface ComponentSchema {
  id: string;                     // 组件唯一 ID
  type: string;                   // 组件类型（如 'hero'、'product-grid'、'features'）
  props: Record<string, any>;     // 组件内容配置（商品来源/标题/图片等）
  style: ContainerStyle;          // 容器样式（背景/边框/圆角/内边距/外边距/阴影）
  elementStyle?: ElementStyle;    // 元素级样式（文字颜色/字号等，由组件自定义）
  animation?: ComponentAnimation; // 滚动进入动画（仅官网组件）
}
```

**SchemaRenderer**：遍历 components 数组，根据 type 从 componentMap 查找组件，注入 props/style/elementStyle/animation 渲染。商城端和官网端共用同一个 SchemaRenderer 组件，只是 componentMap 中注册的组件不同（商城端注册商城组件，官网端注册官网组件）。

#### 4.4.7 3D 动画实验系统（三期）

**技术栈**：
- three.js r184+（WebGL/WebGPU 3D 引擎）
- @react-three/fiber v9.6+（Three.js 的 React 渲染器，v9 稳定支持 WebGPU 后端，GPU 使用降低约 40%）
- @react-three/drei v10.7+（R3F 辅助库：OrbitControls、GLTF 加载、环境光、Float 浮动等）
- @react-three/postprocessing（可选，后期处理：辉光、景深、噪点）

**3D 低代码组件实现**：
- 3D 组件通过 `componentMap` 注册到 SchemaRenderer，内部用 R3F 的 `<Canvas>` 渲染
- `<Canvas frameloop="demand">` 按需渲染，只在 props 变化或动画需要时渲染帧
- 全部 `React.lazy(() => import(...))`，首屏不加载 three.js（约 600KB），3D 组件进入视口附近时才加载
- 移动端自动降级（检测 `navigator.hardwareConcurrency < 4` 或 `deviceMemory < 4GB` 或移动端），替换为 2D 图片/视频/纯 CSS 动画
- 组件卸载时 dispose 所有 geometry、material、texture，防止内存泄漏
- WebGPU 优先：R3F v9 支持 `gl="webgpu"`，浏览器支持时自动用 WebGPU，不支持时回退 WebGL

**3D 场景预设**：

| 预设 | 效果 | 适用场景 |
|---|---|---|
| 粒子网络 | 漂浮的粒子+连线，鼠标交互 | Hero 背景、科技感页面 |
| 浮动几何体 | 多个几何体缓慢浮动旋转 | Hero、产品展示区 |
| 波浪平面 | 起伏的波浪平面，颜色渐变 | 数据/科技主题 |
| 旋转环 | 同心圆环旋转，带粒子 | 产品/技术展示 |
| GLTF 模型 | 上传自定义 3D 模型（产品/Logo） | 产品 3D 展示 |
| 3D 文字 | 3D 立体标题文字，旋转动画 | Hero 大标题 |

**3D 性能优化清单**：
- `frameloop="demand"` 按需渲染
- `dpr={[1, 2]}` 限制设备像素比（移动端 dpr 不超过 1.5）
- 几何体用 `instancedMesh`（重复物体）
- 纹理用 2 的幂尺寸（512/1024/2048），压缩为 KTX2/Basis
- 模型用 Draco 压缩的 GLB，控制在 2MB 以内
- 后期处理（辉光/景深）默认关闭，只在高性能设备开启
- 页面不可见时（`document.hidden`）暂停渲染
- 纯背景 3D Canvas 设 `style={{ pointerEvents: 'none' }}`，不拦截滚动

### 4.5 动画系统（三库分工）

官网对动画要求高，采用**三库分工**，各管一段，避免重复和性能浪费：

| 库 | 职责 | 为什么用它 | 包体积(gzip) |
|---|---|---|---|
| **Lenis** | 平滑滚动（momentum scrolling） | 替代原生滚动，提供丝滑的惯性滚动，和 GSAP ScrollTrigger 完美集成，不破坏 `position: sticky` | ~6KB |
| **GSAP + ScrollTrigger** | 滚动驱动动画（scrollytelling、视差、元素进入视口、数字计数、时间线动画） | 滚动动画的事实标准，性能比 Framer Motion 好（不触发 React reconciler，直接操作 DOM），2026 年所有插件免费（含 SplitText/MorphSVG） | core 23KB + ScrollTrigger 10KB |
| **Framer Motion** | UI 交互动画（弹窗、抽屉、hover、按钮点击、页面转场、AnimatePresence 退出动画） | React 声明式，和 React 状态天然集成，布局动画（layout prop）是 GSAP 做不到的 | ~34KB（tree-shaking 后按需加载可降到 ~15KB） |

**动画实现要点**：

1. **Lenis + GSAP 集成**：Lenis 的 raf 挂到 GSAP ticker 上，`gsap.ticker.add((time) => lenis.raf(time * 1000))`，`gsap.ticker.lagSmoothing(0)` 防止延迟。
2. **ScrollTrigger 与低代码渲染**：组件挂载后（`useLayoutEffect`）再注册 ScrollTrigger，组件卸载时 `ScrollTrigger.kill()` 清理；低代码页面切换时全局 `ScrollTrigger.refresh()` 重新计算位置；图片加载完成后再次 refresh。
3. **数字计数动画**：Stats 组件用 GSAP 的 `gsap.to(obj, { value: target, onUpdate })` 配合 ScrollTrigger，滚动到视口时从 0 动画到目标值。
4. **跑马灯/无限滚动**：LogoWall、Testimonials 的跑马灯用 GSAP 或 CSS animation，不用 ScrollTrigger。
5. **`prefers-reduced-motion`**：全局检测用户系统设置，开启"减少动画"时自动禁用所有非必要动画（Lenis 关闭、GSAP 动画跳过、Framer Motion 动画 duration 设 0、3D 关闭）。
6. **性能预算**：GSAP 动画只操作 `transform` 和 `opacity`（GPU 加速），不操作 `width/height/top/left`（触发重排）。

### 6.3 基础设施

| 项 | 选型 |
|---|---|
| 云服务器 | 阿里云/腾讯云 4C8G 起步（可弹性升配） |
