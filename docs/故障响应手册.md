# LiteShop 故障响应手册

> 本文件定义 LiteShop 项目的故障分级、响应流程、值班制度、postmortem 模板。
> 1a 期上线后必须建立值班制度，1b 期完善 BCP。

---

## 一、故障分级

### 1.1 分级标准

| 级别 | 定义 | 示例 | 响应 SLA | 通知范围 |
|---|---|---|---|---|
| **P0 紧急** | 全站宕机 / 核心功能不可用 / 数据丢失 | API 全部 500 / 支付失败 / 库存超卖 / DB 宕机 | 15 分钟 | 全员 + 管理层 |
| **P1 严重** | 部分功能不可用 / 性能严重降级 | 下单失败率高 / P99 > 5s / 单服务宕机 | 1 小时 | 值班 + 后端组 |
| **P2 警告** | 非核心功能异常 / 性能轻微降级 | 某页面 404 / CPU 高 / 慢查询多 | 4 小时 | 值班 |
| **P3 提醒** | 潜在风险 / 日常告警 | 磁盘 < 15% / 告警恢复 | 不响应 | 邮件 |

### 1.2 核心功能清单（P0 判定依据）

- 商品浏览（H5 首页 + 商品详情）
- 购物车（加购 + 修改 + 删除）
- 下单（创建订单 + 库存锁定）
- 支付（微信 + 支付宝 + 回调）
- 订单管理（H5 查看订单 + 后台发货）
- 用户认证（登录 + 注册 + Token 刷新）

以上功能**全部不可用 → P0**；**部分不可用 → P1**。

## 二、故障响应流程

### 2.1 响应时间线

```
T+0    告警触发（Sentry / Prometheus / 用户反馈）
  ↓
T+5min 值班人确认（电话 / 钉钉）
  ├─ 误报 → 关闭告警 + 记录
  └─ 真实故障 → 升级响应
  ↓
T+15min（P0）/ T+1h（P1）
  值班人初步定位 + 拉群
  ├─ 可快速修复 → Hotfix
  ├─ 需回滚 → 执行回滚 SOP
  └─ 需多人协作 → 拉专家进群
  ↓
T+30min（P0）/ T+2h（P1）
  恢复服务或降低影响
  ├─ 修复完成 → 验证 + 解除告警
  └─ 无法修复 → 降级 + 持续监控
  ↓
T+恢复
  通知用户故障已恢复
  ↓
T+24h 内
  postmortem（P0/P1 必做）
  ↓
T+1 周
  改进项落地
```

### 2.2 值班人职责

**第一响应人**（on-call）：
1. 确认告警真实性
2. 初步定位故障范围
3. 决定 Hotfix / 回滚 / 降级
4. 通知相关方
5. 记录故障时间线

**升级人**（P0 必须升级）：
1. 拉专家进群
2. 协调跨团队协作
3. 对外通告（用户 / 管理层）
4. 决定是否启用 BCP

### 2.3 故障沟通渠道

| 渠道 | 用途 |
|---|---|
| 电话 | P0 紧急通知（无法联系时升级） |
| 钉钉群 | 故障指挥群（P0/P1 全程沟通） |
| 邮件 | 事后 postmortem + 改进项 |
| Status Page | 对外通告（用户可见） |

## 三、常见故障预案

### 3.1 DB 宕机

```
现象：API 全部 500 / DB 连接超时
  ↓
T+0：告警触发（DB 健康检查失败）
T+5min：值班确认
  ├─ 主从切换（如有）→ 切到从库
  ├─ 重启 RDS（阿里云控制台）
  └─ 联系云厂商支持
T+恢复：验证 + 健康检查
```

**预案**：
- RDS 主从架构（生产必配）
- 连接池超时时间 < 5s（快速失败，不拖垮 API）
- 降级：非核心功能（评价/搜索）返回缓存数据

### 3.2 Redis 宕机

```
现象：登录失败 / 限流失效 / 幂等失效
  ↓
T+0：告警触发
T+5min：值班确认
  ├─ 哨兵自动切换（如配）
  ├─ 重启 Redis
  └─ 降级：限流临时关闭 + 幂等走 DB 唯一索引兜底
```

**预案**：
- Redis 哨兵架构（生产必配）
- 幂等双层防护（Redis + DB 唯一索引，见 PRD E16.3）
- 降级：限流临时关闭（接受短时流量上升，保业务可用）

### 3.3 支付回调失败

```
现象：支付成功但订单状态不更新
  ↓
T+0：告警触发（支付回调失败率 > 5%）
T+5min：值班确认
  ├─ 检查回调 URL 是否可达（Nginx + FastAPI）
  ├─ 检查支付平台是否在维护
  └─ 检查幂等表是否阻塞
T+恢复：修复 + 对账（补偿未更新的订单）
```

**预案**：
- 支付平台对账脚本（每日跑，发现差异告警）
- 订单状态补偿任务（定时拉取未更新订单，主动查询支付平台）
- Outbox worker（PRD E9）保证回调最终一致

### 3.4 库存超卖

```
现象：liteshop_stock_oversold_events > 0
  ↓
T+0：告警触发（零容忍）
T+5min：立即排查
  ├─ 定位超卖 SKU
  ├─ 下架商品 + 手动补库存
  └─ 排查并发场景（是否原子 SQL 失效）
T+恢复：修复并发逻辑 + 对账
```

**预案**：
- 原子 SQL（`UPDATE ... SET stock = stock - N WHERE stock >= N`，PRD E3.1.2）
- 库存三层模型（physical / locked / available）
- 超卖零容忍，任何一次都需 postmortem

### 3.5 前端 JS 错误率飙升

```
现象：Sentry 前端错误率 > 1%
  ↓
T+0：告警触发
T+5min：值班确认
  ├─ 检查最新发版（是否新版本引入）
  ├─ 回滚前端版本（如必要）
  └─ 定位错误堆栈 + Hotfix
```

**预案**：
- Source Map 上传到 Sentry（PRD D7.2）
- 前端回滚只需切镜像（不影响 DB）

## 四、BCP（业务连续性计划）

### 4.1 关键资产清单

| 资产 | 重要性 | 备份方式 | RPO | RTO |
|---|---|---|---|---|
| PostgreSQL | 🔴 极高 | 物理备份 + WAL 归档 | 5 分钟 | 30 分钟 |
| Redis | 🟡 高 | 哨兵 + AOF | 1 分钟 | 5 分钟 |
| OSS 图片 | 🔴 极高 | 跨区域复制 | 实时 | 10 分钟 |
| 代码仓库 | 🟡 高 | GitHub / Gitee 双托管 | 实时 | 10 分钟 |
| 镜像仓库 | 🟡 中 | 阿里云 ACR | 实时 | 5 分钟 |

### 4.2 灾备方案

| 场景 | 方案 |
|---|---|
| 单 AZ 故障 | 多 AZ 部署，自动切换 |
| 单 Region 故障 | 跨 Region 备份恢复（RTO 4 小时） |
| 云厂商故障 | 多云备份（长期规划，1a 期不做） |
| 数据被删 | 从备份恢复 + PITR（按时间点恢复） |
| 勒索软件 | 离线备份 + 异地存放 |

### 4.3 灾备演练

每半年演练一次：
1. 模拟 DB 宕机，切到从库
2. 模拟 Redis 宕机，验证降级
3. 模拟单服务宕机，验证自动重启
4. 记录 RTO / RPO，优化灾备方案

## 五、Postmortem 模板

P0/P1 故障恢复后 24 小时内必须完成 postmortem。

```markdown
# Postmortem: {故障标题}

## 摘要
- 故障级别：P0/P1
- 影响范围：{受影响功能 + 用户数}
- 持续时间：{开始时间} - {恢复时间}（共 {N} 分钟）
- 责任人：{postmortem owner}

## 时间线
| 时间 | 事件 |
|---|---|
| T+0 | 告警触发 |
| T+5min | 值班确认 |
| T+15min | 初步定位 |
| T+30min | 开始修复 |
| T+恢复 | 服务恢复 |

## 影响分析
- 用户影响：{多少用户受影响 + 体验降级程度}
- 业务影响：{订单损失 / 支付失败数 / 资金影响}
- 数据影响：{是否有数据丢失 / 不一致}

## 根因分析
- 直接原因：{触发故障的直接操作}
- 根本原因：{为什么会发生（5 why 分析）}
- 放大因素：{为什么影响这么大}

## 修复过程
- 尝试的方案：{逐一列出}
- 最终方案：{实际生效的修复}
- 耗时分析：{哪一步最耗时，为什么}

## 经验教训
- 做得好的：{响应快 / 监控到位 / ...}
- 做得不好的：{定位慢 / 沟通不畅 / ...}
- 运气成分：{是否运气好才恢复}

## 改进项
| 编号 | 改进项 | 负责人 | 截止日期 | 状态 |
|---|---|---|---|---|
| 1 | 加 DB 连接池监控 | @zhangsan | 2026-09-12 | 进行中 |
| 2 | 支付回调自动对账 | @lisi | 2026-09-20 | 待开始 |

## 附录
- 告警截图
- 日志片段
- 监控图表
```

### 5.1 Postmortem 原则

- **对事不对人**：找系统问题，不找责任人
- **根因 > 现象**：5 why 分析，挖到根本原因
- **改进项必落地**：每项有 owner + 截止日期 + 追踪状态
- **公开透明**：postmortem 存档在 `docs/postmortems/`，全员可查

## 六、值班制度

### 6.1 值班排班

| 角色 | 人数 | 轮换周期 | 工作时间 |
|---|---|---|---|
| 第一响应人 | 1 | 每周轮换 | 7×24（含周末） |
| 升级人 | 1 | 每月轮换 | 工作时间 + 紧急可达 |
| DBA | 1 | 固定 | 紧急可达 |

### 6.2 值班人职责

- 保持电话畅通（7×24）
- 15 分钟内响应 P0 告警
- 维护故障时间线记录
- 故障恢复后 24 小时内发起 postmortem

### 6.3 值班交接

每周一上午交接：
- 上周告警汇总
- 未解决的 P2/P3 项
- 待跟进的改进项

## 七、告警降噪

### 7.1 告警聚合

详见 docs/可观测性规范.md §四 告警规则。

### 7.2 误报处理

- 同一告警 24 小时内触发 > 3 次且都是误报 → 调整阈值或禁用
- 误报率 > 30% 的告警规则 → 1 周内必须优化

### 7.3 告警审查

每月审查告警规则：
- 哪些从未触发？→ 删除或降低优先级
- 哪些频繁误报？→ 调整阈值
- 哪些漏报？→ 新增规则
