# LiteShop 部署发布规范

> 本文件定义 LiteShop 项目的部署架构、灰度发布、回滚 SOP、环境隔离细则。
> 与 docs/CI-CD规范.md 配套：CI-CD 管"代码到镜像"，本文件管"镜像到生产"。

---

> **分期适用（唯一事实源：AGENTS.md §十四 运维能力分期适用矩阵）**
>
> | 能力 | 1a 期（必须） | 1b 期 | 增长期（触发：日订单 > 2000） |
> |---|---|---|---|
> | 部署 | Docker Compose 单机 + tag 回滚脚本 + pg_dump 自动备份 | 同 1a | k8s / 蓝绿部署 |
> | 发布 | 脚本部署 + tag 回滚 + 备份后发布 | 同 1a | 4 阶段灰度 |
>
> 本文中超出"1a 期必须"列的内容（k8s 拓扑 / SLB / 蓝绿 / 多阶段灰度 / RDS 主从等）均为**增长期参考**，不作为 1a 期验收项（PRD E15.2 #27 已改为"回滚脚本演练"）。

## 二、发布流程

### 2.1 标准发布（minor/patch）

```
1. 代码合并 main
  ↓
2. 打 tag（v1.2.3）
  ↓
3. CI 触发构建镜像 + 推送仓库
  ↓
4. 部署到 staging
  ↓
5. staging 验证（smoke test + 迁移测试）
  ↓
6. 人工确认 → 部署到 production
  ↓
7. 灰度发布（4 阶段）
  ├─ 1% 流量 → 观察 5 分钟（错误率/延迟/告警）
  ├─ 10% → 观察 10 分钟
  ├─ 50% → 观察 10 分钟
  └─ 100% → 完成
  ↓
8. 健康检查通过 → 发布完成
  ↓
9. 通知群 + 更新 changelog
```

### 2.2 紧急发布（Hotfix）

详见 docs/CI-CD规范.md §六 Hotfix 紧急通道。

```
1. 从 main 拉 hotfix/{issue-id}
2. 最小改动修复
3. 核心验证（backend pytest + 支付/库存单测 + e2e 冒烟）
4. 1 人 review 即可合并
5. 打 v{当前}-hotfix.{N} tag
6. 简化部署：跳过灰度，直接 100%（仅在 P0 场景）
7. 事后 24 小时内补 postmortem
```

### 2.3 破坏性发布（major）

涉及 DB 破坏性迁移或 API 不兼容变更时：

```
1. 提前 7 天公告（钉钉群 + 邮件）
2. 选择低峰期（凌晨 2-4 点）
3. 启用维护页面（503 + Retry-After）
4. 数据库迁移（按 docs/数据库迁移规范.md）
5. 部署新版本
6. 验证 + 解除维护页面
7. 保留旧版本镜像 7 天，随时可回滚
```

## 三、部署前置检查清单

每次发版前必须全部打勾：

### 3.1 代码与测试

- [ ] CI 流水线全绿（lint + test + build + 安全扫描）
- [ ] 代码已合并 main，无未关闭 PR
- [ ] 版本号已更新（package.json / pyproject.toml）
- [ ] CHANGELOG 已更新
- [ ] 数据库迁移已通过 staging 验证（含回滚测试）

### 3.2 配置与密钥

- [ ] `.env.production` 已注入（CORS 收紧 / COOKIE_SECURE=true / 加密密钥已生成）
- [ ] 支付回调 URL 已切换为生产域名
- [ ] Sentry release tag 已设置
- [ ] OSS 内网 Endpoint 已配置

### 3.3 运维准备

- [ ] 回滚预案已准备（上一版本镜像 tag + Alembic downgrade 命令）
- [ ] 监控告警已配置（Sentry release + Prometheus 告警规则）
- [ ] 值班人员已通知（发布窗口 + 联系方式）
- [ ] 备份已完成（DB 全量备份 + WAL 归档确认）
- [ ] 维护页面已准备（如破坏性发布）

## 四、灰度发布详细方案

### 4.1 流量切分（Nginx + Istio / 阿里云 SLB）

```nginx
# Nginx 灰度切分（按权重）
upstream backend {
    server backend-v2:8000 weight=1;   # 新版本 1%
    server backend-v1:8000 weight=99;  # 旧版本 99%
}
```

### 4.2 灰度观察指标

每个阶段必须观察以下指标，任一异常立即回滚：

| 指标 | 正常范围 | 异常阈值 |
|---|---|---|
| 5xx 错误率 | < 0.1% | > 1% |
| P99 延迟 | < 500ms | > 2s |
| 支付成功率 | > 99.5% | < 95% |
| 库存超卖事件 | 0 | > 0 |
| Sentry 新错误 | 0 | > 0 |
| 业务核心流程 | 全部正常 | 任何报错 |

### 4.3 灰度阶段停留时间

| 阶段 | 流量 | 最短观察时间 | 最长停留时间 |
|---|---|---|---|
| 1 | 1% | 5 分钟 | 30 分钟（超时自动推进或回滚） |
| 2 | 10% | 10 分钟 | 1 小时 |
| 3 | 50% | 10 分钟 | 2 小时 |
| 4 | 100% | 30 分钟 | - |

## 五、回滚 SOP

### 5.1 回滚决策树

```
线上问题
  ↓
影响评估
  ├─ P0（全站宕机/支付失败/库存超卖）
  │   └→ 立即回滚 + 通知值班
  ├─ P1（部分功能异常/延迟高）
  │   └→ 评估能否等 Hotfix → 不能则回滚
  └─ P2（视觉问题/文案错误）
      └→ 不回滚，走正常修复流程
```

### 5.2 代码回滚

```bash
# 1. 切到上一版本镜像
kubectl set image deployment/liteshop-backend \
  backend=liteshop-backend:v1.2.2  # 上一版本

# 2. 滚动更新（自动）
kubectl rollout status deployment/liteshop-backend

# 3. 验证
curl https://api.liteshop.com/api/v1/health
```

### 5.3 数据库回滚

详见 docs/数据库迁移规范.md §六 回滚 SOP。

```bash
# 无数据丢失风险
cd backend && alembic downgrade -1

# 有数据丢失风险 → 从备份恢复
psql production < backups/pre_migration_*.dump
```

### 5.4 回滚限制

| 场景 | 能否回滚 | 说明 |
|---|---|---|
| 加字段（可空） | ✅ | 安全 |
| 加索引 | ✅ | 安全 |
| 删字段 | ❌ | 数据已丢，只能从备份恢复 |
| 改字段类型 | ⚠️ | 可能丢数据，需备份恢复 |
| 数据迁移 | ⚠️ | 需反向脚本 |
| 新增 API | ✅ | 代码回滚即可 |
| 删 API | ✅ | 代码回滚即可 |

### 5.5 回滚演练

每季度演练一次：
1. 在 staging 模拟回滚流程
2. 记录 RTO（恢复时间目标）
3. 验证数据一致性
4. 优化回滚脚本

## 六、环境隔离细则

### 6.1 数据隔离

| 维度 | development | staging | production |
|---|---|---|---|
| 数据库 | 本地 PG | 独立 RDS | 独立 RDS（主从） |
| Redis | 本地 | 独立实例 | 独立实例（哨兵） |
| 数据来源 | 假数据 / seed | 脱敏后的生产快照 | 真实数据 |
| 备份 | 无 | 每周 | 每日 + WAL 归档 |

### 6.2 配置隔离

| 配置 | development | staging | production |
|---|---|---|---|
| CORS | localhost | staging 域名 | 真实域名收紧 |
| Cookie | secure=false | secure=true | secure=true |
| 支付 | 沙箱 | 沙箱 | 正式 |
| Sentry | development | staging | production |
| 日志级别 | DEBUG | INFO | INFO |
| 限流阈值 | 宽松 | 中等 | 严格 |

### 6.3 密钥隔离

**红线**：
- 永不共享密钥跨环境（JWT_SECRET / FIELD_ENCRYPTION_KEY / 支付密钥）
- production 密钥用 `FIELD_ENCRYPTION_KEY` 强随机文件密钥（文件权限 600，不入 git / 不入镜像）；云 KMS 为增长期方案（PRD D5.1 分期降级说明）
- staging 密钥独立，不与 production 相同
- 开发者永不在本地配置 production 密钥

### 6.4 网络隔离

- production 数据库仅允许生产 VPC 内访问
- staging 数据库仅允许 staging VPC 内访问
- 永不开放 DB 公网端口（0.0.0.0/0）
- 开发者通过堡垒机 + VPN 访问 production

## 七、发布窗口

### 7.1 允许发布窗口

| 环境 | 允许时间 | 说明 |
|---|---|---|
| staging | 任意 | 无业务影响 |
| production（minor/patch） | 10:00-18:00 工作日 | 避开高峰 + 有人值班 |
| production（major/破坏性） | 凌晨 2:00-4:00 | 低峰期 + 维护页面 |
| production（Hotfix） | 任意 | 紧急通道 |

### 7.2 禁止发布期

- 节假日前 1 天（除 Hotfix）
- 大促期间（双 11 / 618，除 Hotfix）
- 值班人不在岗时
- 错误预算已耗尽时

## 十、project-radar 集成

project-radar skill 检测：
- 是否有 `Dockerfile` → 无则 🔴（无法构建镜像）
- 是否有 `docker-compose.yml` → 无则 🟡
- 是否有部署脚本（`scripts/deploy.ps1` / `deploy.sh`） → 无则 🟡
- 是否有回滚脚本 → 无则 🟡
- 是否定义发布窗口 → 无则 🟡
- `.env.production` 是否在 `.gitignore` → 否则 🔴（密钥泄露）
