## 1. 项目概况

LiteShop 是面向中小商家的轻量级商城系统，当前采用 pnpm + Turborepo monorepo。

技术栈已经按项目宪法确定：

- H5：React 18、TypeScript、Vite、React Router 6、Zustand、TanStack Query
- 后台：React 18、TypeScript、Vite、React Router 6
- 官网：Next.js App Router
- 后端：Python 3.12、FastAPI、SQLAlchemy 2.0 async、Alembic、Redis、Celery
- 基础设施：PostgreSQL 16、Redis 7、Docker Compose

当前项目范围是 PRD v1.3 的一期 1a，13 个计划均已完成初版实现和自动化验收。1b 功能不应在没有重新拆计划和确认范围前混入 1a。

### 2.2 当前代码结构

前端按以下方式组织，后续不要退回到组件内裸请求或通过 `window.location.pathname` 分支：

```text
packages/h5-app/src/
├── pages/       页面视图
├── components/  页面共享组件
├── hooks/       React Query 与交互 Hook
├── service/     API 管理层
├── store/       Zustand 客户端状态
├── utils/       格式化与工具函数
└── router/      React Router 6 集中路由
```

后台保持同样的视图、组件、hooks、service、store、utils、router 分层。

后端保持：

```text
api -> services -> repositories -> models
```

请求/响应使用 Pydantic DTO，写操作使用异步事务，金额使用整数分，类型从 `@liteshop/shared-types` 复用。

## 3. 视觉和编码标准

### 3.1 已确认视觉标准

用户已确认采用 `outputs/miniprogram_ui_gallery_full.html` 的画廊风格，具体表现为：

- 主色基于珊瑚红 `#ff6b6b`，通过 Design Tokens 使用，业务代码不得直接散落硬编码颜色。
- H5 使用窄屏画布、留白、柔和浅色背景、圆角面板、毛玻璃导航和底部 Tabbar。
- 后台沿用同一套 Token，但信息密度更高，优先保证扫描效率和操作效率。
- 色彩、字号、间距、圆角、阴影均从 `packages/shared-tokens/` 和 `docs/设计规范.md` 读取。
- UI 交互遵循 WCAG AA：语义 HTML、键盘可操作、可见焦点、错误/加载/空状态完整。

### 3.2 已确认编码习惯

- 注释使用中文，且只写必要的上下文说明。
- 喜欢清晰的主流分层架构：前端有视图层、组件层、状态数据层、API 管理层、工具层；后端使用 API、Service、Repository、Model 分层。
- 路由使用 React Router 6 集中配置，不使用 `window.location.pathname` 作为页面路由实现。
- 禁止 `any`、禁止重复定义共享类型、禁止组件内裸 Axios。
- 写操作按钮必须防抖，loading 时必须 disabled。
- 金额全链路使用整数分，展示前统一 `formatPrice()`。
- 颜色、间距、字号、圆角、阴影使用 CSS 变量，禁止硬编码视觉值。
- API 必须遵循 `docs/api-contracts/v1/`，统一错误信封和枚举值。
- 代码完成后由主 Agent 主动 review、跑验证、修复问题，再进入下一步。
- 当前更偏好主 Agent 直接推进；过去子 Agent 调度曾出现停滞和交接不完整，因此后续除非明确要求，不要为了形式强行拆子 Agent。

## 5. 当前没有完成的内容

### 5.1 基础设施

- Docker Desktop Engine 当前曾返回 500/无响应，PostgreSQL 16 和 Redis 7 尚未完成本机健康检查。
- 真实生产数据库仓储、真实微信/支付宝 SDK、真实支付沙箱和对象存储尚未接入。
- 当前部分开发路径仍支持内存/演示数据，不能直接作为生产行为。

### 5.2 产品功能边界

- 收藏仍为浏览器本地存储，服务端收藏持久化不属于当前完整交付。
- settings/page schema 仍是开发进程内存存储，重启丢失，多实例不一致。
- 后台销售趋势真实数据尚未完整实现，当前 trend 可能为空。
- 退款只有申请和初始状态，尚未完成渠道退款、Celery worker、成功/失败回写和库存回滚闭环。
- 1b 功能，包括售后、会员、通知中心、评价、商城主题持久化、低代码搭建器、收藏服务化、推荐等，不应假设已经完成。

## 6. 复审发现的生产阻塞项

以下内容来自 2026-09-06 复审结论。结论是：项目目前仍不建议进入生产环境。

### 6.1 高风险问题

1. 支付回调签名仍未覆盖 `providerTradeNo` 和支付渠道，且微信/支付宝共用回调密钥。
2. 创建支付单先返回幂等记录，后校验订单归属，存在跨用户支付单信息泄露风险。
3. 下单商品/SKU 查询未统一限制商品未删除、商品 `ON_SHELF`、SKU `ACTIVE`。
4. 数据库幂等事务无法覆盖 Redis 购物车写入，可能出现接口失败但购物车已修改或重复加购。
5. 未登录用户仍可能被前端显示为订单提交成功，但后端没有创建订单。
6. 下单成功只清理本地 Zustand 购物车，没有删除 Redis 购物车。
7. API 异常时后台和 H5 仍可能静默显示演示数据，生产环境会误导运营人员。
8. 主题配置只写进程内 `_theme`，重启和多实例场景不一致。

### 6.2 中风险问题

1. 短信验证码消费不是原子 GET + DELETE。
2. refresh token 没有真正轮换撤销和重放检测。
3. 未配置可信代理时直接信任 `X-Forwarded-For`。
4. 购物车累计数量没有上限，重复请求可无限累加。
5. 购物车接口大量使用 `HTTPException`，不符合统一错误响应契约。
6. 后台商品搜索参数没有真正传给后端服务层。
7. 后台库存分页缺少 `total` 和 `hasNext`。
8. 后台设置保存失败时仍可能显示“已保存”。
9. 退款状态没有完整推进闭环。
10. 首次并发登录创建用户可能触发唯一索引冲突且未统一转换。

### 6.3 测试与工程不足

- 当前 backend 测试主要是内存模式和 API 冒烟测试。
- `pnpm test` 曾在 Windows Vitest worker 中出现 `VirtualAlloc` 原生崩溃；串行 Turbo 可以通过，但根因仍应评估 CI 资源配置。
- shared-types、shared-components、shared-tokens 缺少有效行为测试。
- 缺少真实 PostgreSQL/Redis 集成测试。
- 缺少并发下单、库存竞争、支付回调竞态、Redis 成功但数据库提交失败、验证码并发消费、商品下架后下单等测试。

5. 实现验证码原子消费、refresh token 撤销/重放检测、可信代理 IP 解析和购物车数量上限。
6. 统一购物车错误响应信封，修复后台商品搜索和库存分页契约。
7. 修复设置保存成功判断，主题配置落库，补齐真实看板趋势数据。
8. 完成退款 worker、渠道调用、状态回写、失败重试和库存回滚。
9. 建立真实 PostgreSQL/Redis 集成测试和并发测试，再重新进行商业级验收。
10. Docker 健康检查恢复后，执行完整的迁移、部署、冒烟和回滚演练。

## 8. 已知错误与规避措施

### 错误一：过早把“构建通过”当成“功能完成”

**表现**：类型、Lint、构建和冒烟测试通过，但复审仍发现支付归属、Redis 一致性、生产回退等问题。

**规避**：以后每个计划至少同时检查业务不变量、失败路径、并发路径、真实数据路径和权限边界；支付、库存、订单不能只看 happy path。

### 错误二：开发回退逻辑没有严格隔离

**表现**：API 异常时使用演示数据或内存状态，容易把“开发体验”带进生产行为。

**规避**：所有 demo fallback 必须由显式开发开关控制，生产环境默认关闭；接口异常必须显示错误、重试和数据不可用状态。

### 错误三：只清理前端状态，没有核对服务端状态

**表现**：下单后只清理 Zustand，没有同步清理 Redis 购物车。

**规避**：每个跨存储写流程都要列出本地状态、Redis 状态、数据库状态和失败补偿路径，至少有集成测试覆盖部分成功。

### 错误四：交互改动引入了 effect 无限更新

**表现**：购物车未登录分支中，临时空数组每次渲染引用变化，导致 `Maximum update depth exceeded`。

**规避**：effect 依赖必须使用稳定引用；状态更新前比较新旧值；浏览器控制台必须作为 UI 验收的一部分，而不是只看页面是否渲染。

### 错误五：子 Agent 调度和交接信息不稳定

**表现**：子 Agent 曾出现执行停滞、正式摘要缺失、需要用户反复询问进度。

**规避**：当前阶段优先由主 Agent 直接执行；如果未来重新使用子 Agent，必须限制单批范围、明确完成回执、主 Agent 主动验收并自动推进，不能依赖用户轮询。

### 错误六：全量验证并发导致 Windows Node 原生内存耗尽

**表现**：并行 Turbo 执行时出现 `VirtualAlloc`、V8 OOM 和 worker 崩溃。

**规避**：Windows 本地默认使用 `turbo --concurrency=1` 或分包验证；CI 再根据机器资源配置并发度，不能把并发崩溃误判为代码失败，也不能忽略资源问题。
