# LiteShop 前后端架构说明

## 1. 选型结论

LiteShop 采用“按职责分目录、按页面聚合视图”的结构。它保留了 `crm-frontend-admin` 中直观的 `pages / components / hooks / service / store / utils` 习惯，同时使用 LiteShop 宪法规定的 React 18、React Router 6、TypeScript、React Query 和 Zustand。

页面组件不读取 `window.location.pathname` 做分流。所有 URL 由 `src/router` 中的 `createBrowserRouter` 管理，页面跳转使用 `Link` 或路由导航 API。

## 2. 前端目录约定

```text
packages/h5-app/src/
├── App.tsx                 # 应用根组件与全局 Provider
├── router/                 # React Router 6 路由表
├── pages/                  # 页面视图；一个业务页面一个目录
│   ├── home/
│   ├── product-detail/
│   ├── cart/
│   └── order-confirm/
├── pages/*/components/     # 仅供当前页面使用的局部组件
├── components/             # 跨页面通用展示组件
├── hooks/                  # 可复用交互 Hook（防抖、查询等）
├── service/                # Axios 客户端与 API 方法；禁止页面裸请求
├── store/                  # Zustand 客户端状态；不存放服务端缓存
├── utils/                  # 无副作用纯函数（金额、日期、格式化）
├── assets/                 # 图片、图标等静态资源
└── styles.css              # 应用样式与设计 Token 引用
```

Admin 使用相同结构：`pages/dashboard`、`pages/products/editor`、`pages/orders`、`pages/inventory`、`pages/settings`。页面私有组件必须放在对应页面目录，不把业务状态塞进全局 `components`。

数据流固定为：

```text
pages -> components/hooks -> service (API)
pages -> store (客户端状态)
service -> @liteshop/shared-types
```

React Query 管理 API 请求、缓存、失效和 mutation（写操作 `retry: 0`）；Zustand 只管理购物车选择、会话令牌等客户端状态。所有写按钮使用 `useDebounceAction`，金额在 API 和状态中均为整数分。

## 3. 后端目录约定

```text
backend/app/
├── main.py                 # FastAPI 应用组装、路由注册、中间件
├── api/                    # HTTP 适配层：参数、认证、响应 DTO
├── schemas/                # Pydantic 请求/响应模型
├── services/               # 用例和领域规则：订单状态机、库存、支付
├── repositories/           # SQLAlchemy 查询与持久化，不承载业务决策
├── models/                 # SQLAlchemy ORM 模型
├── core/                   # 配置、数据库会话、Redis、安全、日志
├── tasks/                  # Celery 异步任务
├── enums/                  # 共享领域枚举
└── errors/                 # 统一 ApiError 与错误码映射
```

后端调用方向固定为：`api -> services -> repositories -> models`。`api` 不直接查询 ORM，写操作必须在异步事务中执行；仓储接收 `AsyncSession`，由服务层决定事务边界。数据库使用 PostgreSQL 16，Redis 7 用于缓存、锁和五分钟幂等键。API 响应使用统一 envelope，时间使用带时区 ISO8601，日志使用结构化字段 `request_id / event / user_id`。

## 4. 与参考后端的对照

`F:\商城小程序\backend` 的 `api / core / models / schemas / services` 目录划分是合理的，适合作为认知模型；但当前实现有以下 LiteShop 不可继承的差异：

- `async def` 中调用同步 SQLAlchemy Session，会阻塞事件循环；LiteShop 使用 `AsyncSession` 和 `asyncpg`。
- 使用 SQLite 和 Decimal 元字段；LiteShop 数据库存储整数分，展示时才格式化。
- 订单、库存、优惠券扣减主要写在 API 函数中；LiteShop 必须下沉到 service/repository，并由事务统一锁定、回滚和幂等。
- `except:` 静默吞错、开发密钥默认值和整数状态码不满足安全与状态机约束；LiteShop 使用统一错误码、枚举状态和环境密钥。

因此 LiteShop 采用“相同目录认知 + 不同运行时约束”的兼容方案：你可以按 CRM 项目的方式快速定位文件，但业务正确性由异步分层、契约类型和事务规则保证。

## 5. 迁移规则

新增页面先在 `pages/<业务>` 建立视图，再把页面专属组件放入其 `components`；新增接口先在 `service` 建立方法和类型，禁止在 JSX 内调用 Axios；跨页面状态才进入 `store`；纯计算才进入 `utils`。公共类型一律从 `@liteshop/shared-types` 导入，禁止在 H5/Admin 重复声明领域枚举或金额模型。
