# LiteShop 数据库迁移规范

> 本文件定义 LiteShop 项目的 Alembic 迁移命名、评审、执行、回滚 SOP。
> 主 Agent 在 plan-04 backend 骨架阶段生成 `alembic.ini` + `backend/alembic/` 目录，子 Agent 写迁移必须遵循本规范。

---

## 一、迁移文件命名规范

### 1.1 revision id 规约

Alembic 默认生成随机 hash（如 `a1b2c3d4e5f6`），**禁用随机 id**，改为语义化命名：

```bash
# 正确：{yyyymmdd}_{简短描述}
alembic revision -m "20260901_create_orders_table"
alembic revision -m "20260905_add_status_index_to_orders"
alembic revision -m "20260910_add_encrypted_phone_to_users"

# 错误：随机 hash + 无意义命名
alembic revision -m "create table"  # ❌ 哪个表？
alembic revision -m "fix bug"       # ❌ 什么 bug？
```

### 1.2 文件名格式

```
backend/alembic/versions/
├── 20260901_120000_create_orders_table.py
├── 20260905_143000_add_status_index_to_orders.py
└── 20260910_090000_add_encrypted_phone_to_users.py
```

- 文件名前缀：`{年月日}_{时分秒}_`，保证迁移顺序明确
- `down_revision` 必须指向最近一次迁移，**禁止分叉迁移链**

### 1.3 迁移描述命名模板

| 操作类型 | 命名模板 | 示例 |
|---|---|---|
| 建表 | `create_{table}_table` | `create_orders_table` |
| 加字段 | `add_{column}_to_{table}` | `add_encrypted_phone_to_users` |
| 加索引 | `add_{index}_index_to_{table}` | `add_status_index_to_orders` |
| 改字段 | `alter_{column}_on_{table}` | `alter_price_on_order_items` |
| 删字段 | `drop_{column}_from_{table}` | `drop_legacy_status_from_orders` |
| 数据迁移 | `migrate_{描述}` | `migrate_order_status_to_5_states` |

## 二、迁移评审清单（合并前必检）

每个数据库迁移 PR 必须通过以下检查，**不通过则 CI fail + 禁止合并**：

### 2.1 可回滚性

- [ ] `upgrade()` 有对应的 `downgrade()` 实现
- [ ] `downgrade()` 能在 staging 完整跑通（`alembic downgrade -1`）
- [ ] 删字段/删表的 `downgrade()` 必须保留备份表或能重建

### 2.2 性能安全

- [ ] 加字段必须 `nullable=True` 或 `server_default=值`，**禁直接 NOT NULL 加字段**
- [ ] 加索引操作不锁表（PostgreSQL 11+ `CREATE INDEX CONCURRENTLY`）
- [ ] 大表（预估 > 10 万行）改字段类型必须用 `USING` + 分批执行
- [ ] 删字段前确认无业务依赖（Grep 全代码库搜索该字段名）

### 2.3 数据完整性

- [ ] 新建外键约束必须先加索引（FK 列无索引会导致父表写锁）
- [ ] 数据迁移类必须先在 staging 跑一次，输出迁移行数对比
- [ ] 枚举值变更必须同步更新 `packages/shared-types/`（见 §四 枚举同步）

### 2.4 依赖检查

- [ ] 迁移不依赖业务代码（迁移文件只写纯 SQL/ORM，不 import service 层）
- [ ] 迁移不依赖其他迁移的中间态（只依赖最终的 schema 状态）

## 三、执行 SOP

### 3.1 开发环境

```bash
cd backend
alembic upgrade head    # 应用所有迁移
alembic current         # 查看当前版本
alembic history         # 查看迁移链
```

### 3.2 staging 环境（每次发版前）

```bash
# 1. 从 production 导出最新 schema 快照
pg_dump --schema-only production > staging_schema.sql

# 2. 在 staging 恢复
psql staging < staging_schema.sql

# 3. 跑待发布的迁移
alembic upgrade head

# 4. 跑回滚测试
alembic downgrade -1
alembic upgrade head    # 再升回去

# 5. 验证数据完整性
pytest tests/test_migration_{migration_name}.py
```

### 3.3 production 环境（发版时）

```bash
# 1. 备份（必须，红线）
pg_dump production > backups/pre_migration_$(date +%Y%m%d_%H%M%S).dump

# 2. 应用迁移（在维护窗口期，如有破坏性变更）
alembic upgrade head

# 3. 健康检查
curl https://api.liteshop.com/api/v1/health

# 4. 失败立即回滚
alembic downgrade -1
psql production < backups/pre_migration_*.dump
```

## 四、枚举同步规约

数据库枚举变更必须同步三层：

```
DB enum（PostgreSQL）
  ↓
Python enum（backend/app/enums/）
  ↓
TS enum（packages/shared-types/src/enums/）
```

### 4.1 同步流程

1. 迁移文件里修改 DB enum：`ALTER TYPE order_status ADD VALUE 'shipped'`
2. 同 PR 内更新 `backend/app/enums/order_status.py`
3. 同 PR 内更新 `packages/shared-types/src/enums/order-status.ts`
4. CI 自动跑 `python scripts/check_enum_sync.py` 校验三层一致

### 4.2 删枚举值（高风险）

PostgreSQL 不支持直接删 enum value，必须：
1. 新建临时 enum 类型
2. 迁移数据到新类型
3. 删旧类型，重命名新类型
4. **只删已废弃 3 个月以上的值**，活跃值禁删

## 五、大表加字段策略（> 10 万行）

### 5.1 禁用方式

```sql
-- ❌ 禁止：直接加 NOT NULL 字段，会锁整表
ALTER TABLE orders ADD COLUMN tracking_no VARCHAR(50) NOT NULL;
```

### 5.2 推荐方式（3 步走）

```sql
-- Step 1：加可空字段（瞬时完成，不锁表）
ALTER TABLE orders ADD COLUMN tracking_no VARCHAR(50);
-- alembic 迁移 1

-- Step 2：分批回填数据（每批 1000 行，事务控制）
-- alembic 数据迁移（命名 migrate_backfill_tracking_no）
DO $$
DECLARE
  batch_size INT := 1000;
  affected INT;
BEGIN
  LOOP
    UPDATE orders SET tracking_no = 'PENDING'
    WHERE tracking_no IS NULL
    LIMIT batch_size;
    GET DIAGNOSTICS affected = ROW_COUNT;
    EXIT WHEN affected = 0;
    PERFORM pg_sleep(0.1);  -- 降低主库压力
  END LOOP;
END $$;

-- Step 3：加 NOT NULL 约束（数据已满，瞬时完成）
ALTER TABLE orders ALTER COLUMN tracking_no SET NOT NULL;
-- alembic 迁移 3
```

### 5.3 加索引策略

```sql
-- 大表加索引必须 CONCURRENTLY，不锁表但耗时较长
CREATE INDEX CONCURRENTLY idx_orders_status ON orders(status);
-- 注意：CONCURRENTLY 不能在事务内跑，迁移文件需设 transaction_per_migration=False
```

## 六、回滚 SOP

### 6.1 代码回滚 + DB 回滚协同

| 场景 | 代码 | DB | 操作 |
|---|---|---|---|
| 加字段（可空） | 回滚到上一版 | downgrade | 安全，无数据丢失 |
| 加字段（NOT NULL） | 回滚到上一版 | 先删 NOT NULL 约束再 downgrade | 需确认无依赖 |
| 删字段 | 回滚到上一版 | 无法恢复数据 | **不可回滚**，需从备份恢复 |
| 加索引 | 回滚到上一版 | downgrade | 安全 |
| 改字段类型 | 回滚到上一版 | 数据可能丢失 | 需从备份恢复 |
| 数据迁移 | 回滚到上一版 | 反向数据迁移 | **高风险**，需写反向脚本 |

### 6.2 回滚决策树

```
线上发版后发现问题
  ↓
影响范围评估
  ├─ 无数据丢失风险（加字段/加索引）→ alembic downgrade + 代码回滚
  ├─ 有数据丢失风险（删字段/改类型）→ 从备份恢复（不回滚迁移）
  └─ 数据迁移类 → 跑反向脚本（如已准备）+ 代码回滚
```

### 6.3 备份策略

| 备份类型 | 频率 | 保留期 | 用途 |
|---|---|---|---|
| 全量逻辑备份 | 每次迁移前 | 7 天 | 迁移回滚 |
| 全量物理备份 | 每日 | 30 天 | 灾难恢复 |
| WAL 归档 | 实时 | 7 天 | PITR（按时间点恢复） |

RPO ≤ 5 分钟（WAL 归档），RTO ≤ 30 分钟（从物理备份恢复）。

## 七、常见坑点

### 7.1 迁移链分叉

**现象**：两个子 Agent 同时写迁移，`down_revision` 都指向同一个父迁移，导致链分叉。

**解决**：数据库迁移必须**串行执行**（主 Agent 调度），子 Agent 不能并行写迁移文件。如需并行，主 Agent 先建空迁移占位，子 Agent 填内容。

### 7.2 迁移依赖业务代码

**现象**：迁移文件 `from app.services import order_service`，业务代码改动后迁移跑不通。

**解决**：迁移文件只写纯 SQL 或裸 SQLAlchemy Table 定义，**禁 import service/repository 层**。

### 7.3 忘记更新 shared-types

**现象**：DB enum 加了值，前端 TS enum 没同步，运行时 `undefined`。

**解决**：CI 跑 `python scripts/check_enum_sync.py` 自动校验，不一致则 fail。

### 7.4 CONCURRENTLY 在事务内失败

**现象**：`CREATE INDEX CONCURRENTLY` 在 Alembic 默认事务内报错。

**解决**：迁移函数加 `with op.get_context().autocommit_block():`。
